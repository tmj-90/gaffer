## [Unreleased]

### Added

- **`wg block` and `wg unblock` for people.** `gaffer wg block <n> --reason …` always acted as an agent and failed `CLAIM_REQUIRED`, `ticket move <n> blocked` from ready was an illegal transition, and there was no unblock command (the runner's park reasons said "then unblock" without naming one). Without `--token`, `wg block` now acts as you (`$USER`) and parks a draft, refining, ready or by-hand (`human-claim`) ticket; `gaffer wg unblock <n>` returns a blocked ticket to draft or refining when that is where you blocked it from, otherwise to ready (its ready gate applies), and `--to ready|refining|draft` picks. The new state-machine edges (`draft|refining|ready -> blocked`, `blocked -> draft`) are legal only on this path and only for a human or admin actor, so a board drag still cannot take them and an agent still blocks only its own claim with its token. The park reasons now say `then unblock it ('gaffer wg unblock <n>')`, and the no-local-checkout park names commands that exist (`gaffer onboard <dir>` and `wg ticket repo-access set`, not a `repo update` there is no such command for). Unblock goes back to where the ticket was last blocked from, whichever path blocked it. Each writes `ticket.blocked` (with the status it left) or `ticket.unblocked`. Test: `cli-human-block.test.ts`.

- **Tickets and their criteria can be edited until they are claimed.** A ready-gate refusal on a missing field could not be fixed: there was no way to set a description, a verification method or a policy after `ticket create`, so the only way out was won't-do and re-create. Now `gaffer wg ticket edit <n> [-t title] [-d description] [-p policy] [--priority n]`, `gaffer wg ac edit <n> <ac> [-t text] [--verify method] [--check cmd] [--clear-check]` and `gaffer wg ac rm <n> <ac>` (`<ac>` is the criterion's position, 1 for the first, or its id), and over REST `PATCH /tickets/{id}`, `PATCH /tickets/{id}/acceptance-criteria/{acId}` and `DELETE /tickets/{id}/acceptance-criteria/{acId}` (in docs/openapi.json). Each writes an event (`ticket.edited` with the old and new values, `ac.edited`, `ac.removed`), and an edited criterion goes back to pending. `ticket create` (and `POST /tickets`) warns `DESCRIPTION_REQUIRED` when a `team_light`-or-stricter ticket has no description. An edit to a ready ticket must keep it passing its ready gate (otherwise `POLICY_DENIED` and nothing changes). The quickstart's strict-pack recipe now covers every refusal (`ticket edit -d`, `set-reviewer` without the `--admin` it never needed, `ac edit --verify`, `approve-ready` for `regulated`), and a test runs it as written. Test: `ticket-contract-edit.test.ts`.

- **Acceptance records only the tester's test files that actually ran (external review #7).** The merge gate's tester replay ran the repository's registered test command and read only its exit code: with a file-scoped command (`node --test test/label.test.mjs`) the tester's `test/acceptance.test.mjs` never executed, the run passed, the landing recorded that file as passed on the landed revision, the broken combination landed and `wg stats` counted the epic as accepted. The replay (`lib/tester-replay.mjs`, both landing paths) now runs the tester's files **by path** with the stack's runner where a file-scoped invocation is well defined — node:test `node --test <files…>` (the registered command's loader flags kept), vitest `vitest run <files>` and jest `--runTestsByPath` with a JSON report, pytest with its node ids, `go test` on the files' packages after `go list` names their test files, `cargo test --test <name>` for `tests/<name>.rs` — in the scratch merge worktree through `bin/dod-regate.sh` (the gates' sandbox wrap and timeout; the test command is read from the gated target's package.json, never the branch's). Where no file-scoped invocation is known the registered command runs, with a node:test reporter added through `NODE_OPTIONS`. Either way each tester file needs the runner's own evidence that it ran; a file without it is not a pass: the landing is held (*blocked*, `tester_replay_unverified`, the files named in the hold reason, the `TESTER REPLAY UNVERIFIED` evidence and a new *landings held by the tester replay* section of `gaffer status`), nothing lands and no replay record is written. The record lists only files proven to have run and passed. The proof is hard to forge from the code under test: node:test events are lines the reporter signs (HMAC-SHA256) with a per-replay key it deletes from its environment before any test file starts, with a per-process sequence and closing count; a by-path run that reports a file it was not given, a vitest/jest report naming other files or miscounting, or pytest/cargo naming an unrequested file makes the whole replay unverified, and plain output text never counts (a delivery whose module exits before the tester's tests register and prints "passed" lines and reporter-shaped events for them used to land and be recorded; `land-tester-replay.test.sh` K and `tester-replay-proof.test.mjs` P7 pin it). Fail-closed and compare-and-land are unchanged. In the reviewer's fixture the tester's file now runs on the candidate and fails there (`tester_replay_red`), so the epic is not counted; `runner/test/land-tester-replay.test.sh` (I, J), `e2e-release-gate-tester-replay.test.sh` (step 5) and `tester-replay-proof.test.mjs` pin it.

- **An approval covers every write repository, and done means every one landed (external review #7).** With a two-repo ticket whose B delivery branch was briefly missing (or whose checkout was unreadable) at approval time, the Review button offered *Approve and land now … repoB lands after it*, the approval pinned only A, the landing merged A and marked the ticket done with B's change still on its branch, and Poll for work then reported `no_work` while `gaffer merge` would have finished B. Now: (a) `approveReview` refuses (`409 STATE_CONFLICT`, `details.reason` `repo_unavailable`, naming each repo and why: no checkout on this machine, an unreadable path, no delivery branch, a branch git cannot find) while any active write repo's delivery head cannot be resolved — for a human and an agent, through REST, the CLI and the runner's review pass — and approves nothing; (b) the Review button reads the same rule (`approve_outcome.kind` `held_repo_unavailable`, *Approve held: repoB unavailable*, disabled; it never says "land now"); (c) `computeLandingStatus` lists every write repo of a per-repo approval, so a write repo with no review pin (an approval made the old way) is pending (`pinned: false`, `unpinned`), `mark-merged` refuses with `partial_landing` naming it, `landing_state` reads *Held · approval does not cover every repository*, and the landing paths hold on it (`lib/land.sh`, `lib/tester-binding.mjs` — never a head landing for a repo nobody approved); (d) a *partly landed* ticket is merge work under the same policy as any approval, decided again when the lane runs: with a human approval and Auto-merge on (or an earned merge grant) the dashboard's Poll for work counts it, `bin/poll-once.sh` clears the merge lane's per-run held list, the merge lane lands the remaining repositories through the merge gate and the tester replay (a landed one is never merged again), and a tick that only landed reports `TICK_RESULT=merged`, not `no_work`; with Auto-merge turned off since, or an agent approval whose `MERGE_ON_AGENT_REVIEW` was withdrawn, it stays *Approved · partly landed* (its status says so) for a human's Merge now. A write repo with no checkout on this machine now holds the approval (it could never land); the refusal says what to do: attach its checkout, or make it read-only on the ticket (`wg ticket repo-access set <n> <repo> --access read`; a read-only repo never blocks). The runner's agent reviewer reads only the primary repository, so dispatch refuses its approval of a multi-repo ticket: the refusal is now noted on the ticket (not only in the log) and a later run does not spend another review call on the same head. `runner/test/e2e-multi-repo-delivery.test.sh` runs the reviewer's sequence through both landing paths and the dashboard's Poll.

- **A red tests gate under a worker pool is rerun once at concurrency 1 before the attempt counts.** With `GAFFER_MAX_DELIVERY_ATTEMPTS=3` a test that races for a port or CPU under `GAFFER_CONCURRENCY>1` could park a correct delivery. `runner/lib/dod.sh` now reruns a failing tests gate (never typecheck or lint) once, only when the run was under a pool: one rerun at a time across the pool (a lock in `$GAFFER_DATA/.dod-serial`), after the other workers' in-flight gate runs finish (`GAFFER_DOD_RERUN_WAIT`, 120 s) while new gate runs wait for it, with serial hints in the test's env (`GAFFER_DOD_SERIAL=1`, `RUST_TEST_THREADS=1`, `PYTEST_XDIST_AUTO_NUM_WORKERS=1`). A pass on the rerun is PASS marked `flaky-suspected` (the GATE row's 8th column, after gate integrity's `source` in the 7th; `flaky: true` in the DoD evidence JSON), its note naming both runs and run 1's output kept in a `---DOD-RERUN---` block; `tick.sh` files a `needs_human_review` note and the Review card shows a yellow "Flaky suspected" card. A second red is the failure, naming both exit codes; a lock that cannot be taken in time leaves run 1's FAIL standing. `GAFFER_DOD_FLAKY_RERUN=0` turns it off. Tests: `runner/test/dod-flaky-rerun.test.sh` (unit cases plus a real tick under a pool of 2), `web-dod-checklist.test.ts`.

- **Provenance trailers on every merge commit.** `bin/merge-ticket.mjs` wrote no trailers, so `git log` could not say which ticket a merge was or who approved it. Every landing path now writes three git trailers read from the dispatch DB (`runner/lib/provenance-trailers.mjs`): `Gaffer-Ticket: #N`, `Gaffer-Reviewed-By: human:<id>` / `agent:<id>` (the actor of the latest approval; `none recorded` otherwise) and `Gaffer-Gates` (the runner's DoD verdict per gate, gate integrity's advisory row included so a FLAG is named, the acceptance-criteria count, and the tester's verdict taken from the tester's own `tester_passed` / `tester_failed` transition since the latest approval, `(human)` when a human recorded it; a test_output evidence row, which a delivery agent can write through `record_ac_evidence`, never counts). The merge lane and the AFK review pass (`lib/land.sh` → `_gaffer_merge_gate`), the dashboard's Merge button and `gaffer merge` (`gateProposedMerge`) write them into the merge gate's gated merge commit, the commit that lands, and the PR path puts them in `gh pr merge --body` (not for a rebase). While trailers are on that gated merge is `--no-ff`, so a merge commit exists to carry them. No model name is written, values are flattened to one printable line, and the trailers are unsigned. `GAFFER_PROVENANCE_TRAILERS=0` restores the plain message and the fast-forward. Tests: `runner/test/provenance-trailers.test.mjs`; `merge-lane.test.sh` checks a real landing and the off switch; `merge-ticket.test.mjs` checks the PR body.

- **The last allowed attempt's failure is on the rework trail.** When the attempt that used up `GAFFER_MAX_DELIVERY_ATTEMPTS` (or the rework budget, or repeated the previous failure) failed, `tick.sh` parked the ticket without a trail entry, so the ticket page showed "Attempt 3/3 not taken" for an attempt that was tried, or listed its run as "No failure recorded". The park now files that failure first, with its gate (`definition-of-done`, `agent-env-install`, …) and the distilled output, numbered like every other entry (the failure of attempt N as N+1). `wg runner-rework --final` appends only the trail row: no "reworking" card and no `ticket.reworking` event. The page shows it as "Attempt 3/3 · <gate> failed", with the model and CLI only when that attempt's agent ran. A parked ticket's trail (and the rework counts read from it: the bouncing-tickets signal, spec-clause bounces, health) now includes its final failure. Test: `runner/test/rework-final-trail.test.sh`.

- **Each attempt records its model and its CLI version.** Every usage-ledger row made through the worker seam (`lib/worker.sh` `worker_deliver` → `gaffer_usage_record`) now carries `model_requested` (the routed `--model`, or `default`) beside the measured `models` map, `claude_version`, and for a delivery its `attempt`. The version comes from `runner/lib/claude-version.mjs`: read from a native or npm install without running the binary, else `claude --version` (once per tick); a shell-script wrapper is not run and reads `unknown (wrapper script)`, and `GAFFER_CLAUDE_VERSION` pins it (the docker sandbox's image CLI). After each delivery attempt `tick.sh` attaches agent-run evidence (`evidence_type: log`, payload `kind: agent_run`; `wg attach-evidence` gains `--payload-json`, a JSON object of at most 4 KB), and the ticket page's Attempts history shows "Model … · CLI …" on every attempt, failed or not. A failure is paired with the run of the attempt that failed: the latest run recorded before it whose attempt is one less than the trail's (the runner files a failure under the next attempt's number), so an attempt that failed before its agent was launched (`agent-env-install`) names no model rather than the previous attempt's; each failure row is numbered by the attempt that failed (it read one higher, so the failure of attempt 1 and the attempt 2 that passed were both "Attempt 2"); every run no failure is paired with (the attempt that passed after a failed one) follows the failures on its own row, and the "not taken" kicks, which were never drawn (passed to `el()` as extra arguments), now show for the attempts left, and only runner-recorded rows (actor `system`) count, so an agent cannot put a model name on its own attempt. Tests: `runner/test/attempt-provenance.test.sh` (a real tick with a stub agent), `evidence-payload.test.ts`, `web-attempt-provenance.test.ts`; the UI regression checks the ticket page.

One resolver pass per ticket (`$GAFFER_DATA/.merge-conflict-resolved`, not reset per run): a second conflict waits for a human, as before. `GAFFER_CONFLICT_RESOLVER=0` turns it off; `GAFFER_MERGE_TIMEOUT_MS` bounds it. The resolver's turn is now ledgered (`kind: merge-resolver`) so it counts toward the caps and the cost views; it was the one paid agent call the ledger never saw. `runner/test/merge-lane.test.sh` E and F prove the path against the real tick with a resolving stub.
- **`gaffer wg`, `gaffer approve`, `gaffer merge`: the whole first run from one front door.** A fresh operator following the quickstart could set up, onboard, open the dashboard and go live, but nothing said how to create the first ticket for the onboarded repo (the raw path was four `node packages/dispatch/dist/cli/index.js --db .gaffer/dispatch.sqlite …` commands) or how to land a ticket a human had approved without the dashboard's Merge button. `runner/gaffer wg <args>` is the dispatch CLI pinned to this factory's database; `runner/gaffer approve <n> [--reviewer <you>]` records a human approval (`in_review → ready_for_merge`); `runner/gaffer merge <n>` runs exactly what the dashboard's Merge button runs (`bin/merge-ticket.mjs`: conflict-safe merge, mark done, digest + ledger refresh, branch delete). `gaffer help` now lists these and the previously undocumented `gaffer run [--daemon]`. The quickstart gains **§4 Give it your first ticket** (the four commands and the rules the `ready` gate enforces), **Approve and merge** under the run step, the onboarding-intake decision that onboarding files, and uses `gaffer run` throughout; the README's quickstart block follows the same path. Verified by following the documents literally in a fresh clone: setup → onboard → dashboard → demo → ticket → `gaffer run` → `approve` → `merge` → the change on the repo's `main` with its tests green.
- **A merge lane: what is approved lands, whoever approved it.** The agent review pass merged only the tickets it approved itself. A ticket a human approved (dashboard, `wg review approve`) or the independent tester passed reached `ready_for_merge` and then waited for the dashboard's Merge button, in autonomous mode too: a live run stalled with nine dependents starving behind a human-approved bootstrap, and with the tester lane on every ticket would have stopped there. `runner/lib/merge-lane.sh` now runs at the start of every tick, asks the same merge policy the review pass asks (`wg ticket auto-decision --gate merge`: the env floor or an earned per-repo/risk grant, no policy of its own) and lands each permitted ticket through the shared `gaffer_land_delivery` (`runner/lib/land.sh`, lifted verbatim from the review pass: PR or local safe-merge, mark-merged, card refresh, digest, push, branch delete), before the candidate scan so the merge frees its dependents in the same tick. A held ticket is logged once per run and left for a human. `GAFFER_MERGE_LANE=0` disables it. `runner/test/merge-lane.test.sh` proves it against the real tick.
- **Waste controls for the capped budget: a hard stop no longer throws the work away.** When a delivery turn dies on the per-tick turn cap, the daily USD cap or the wall-clock timeout, the runner now commits whatever the agent left uncommitted in the worktree as a `wip:` checkpoint on the ticket branch before pausing, and the ticket pauses with the real reason (`cap_hit`, `budget_cap` or the new `timeout`; schema v25 widens the pause table). **Continue** re-enters the SAME branch: every retry (a rework, a failed gate, a timeout) keeps the branch's previous commits and the prompt tells the agent so ("the previous attempt's commits are already on this branch: fix them in place; run `git log --oneline` first"), instead of the old clean-slate reset to base that re-spent the whole budget re-implementing what had already been built. `GAFFER_RETRY_FRESH_BRANCH=1` restores the reset. - **Hybrid lore retrieval.** `search_lore` / `memory search` now fuse the FTS5 bm25 ranking with a dense vector per record (memory migration 013, `lore_embeddings`), so a typo beside a real term, a joined or split compound (`ratelimiting`, `time out`) or a subword (`argon 2id`) still finds the record that pure keyword matching missed. The built-in embedder is a deterministic hashed n-gram space (word unigrams/bigrams + character trigrams, signed hashing, 256 dims): no model, network or credential, microseconds per record, vectors as portable as the SQLite file. It captures surface similarity, not meaning; a model-backed embedder plugs in behind the same `Embedder` interface and re-embeds lazily under its own `model` id. Fusion is magnitude-preserving (top lexical hit = 1, dense capped at 0.5) so a dense-only near-miss can outrank only a weak keyword hit, and the existing trust re-rank applies unchanged; dense candidates pass the same repo / tag / kind / status filters and a cosine floor keeps a genuinely unknown topic at zero hits (the absence-marker path survives). ### Security

- **A ticket's contract is frozen once it is claimed.** `POST /tickets/{id}/acceptance-criteria` had no status check: a done ticket accepted a new pending criterion, and a factory MCP mount scoped to its own `in_review` ticket added `check_command: "echo pwned"`, after which every human approve was refused `AC_CHECK_UNVERIFIED`. Every contract write (title, description, policy, adding, editing or removing a criterion, check commands) is now refused from `claimed` on (claimed, in_progress, in_review, in_testing, ready_for_merge, done, cancelled, failed, paused) with `409 CONTRACT_FROZEN`, on the CLI, over MCP and over REST, because the review and the tester are bound to the contract the delivery saw. Draft, refining, ready and blocked stay editable. The test contract (`wg ticket test-contract`, MCP `set_test_contract`, `POST /tickets/{id}/test-contract`) is part of the tester's contract hash, so it follows the same rule from the point the tester takes over: whoever hands the ticket to the tester (the implementer, the reviewer or you) can still write it through `in_review`, and from `in_testing` on it is refused with `CONTRACT_FROZEN`. A runner tick re-reads the ticket right after its claim, so the delivery prompt carries the contract as frozen, not as the candidate scan saw it a moment earlier. Tests: `ticket-contract-edit.test.ts`, `cli-edit-review.test.ts`.

- **The Docker build context is an allow-list (external review #9).** `.dockerignore` was a deny-list that named neither `./repos` nor `.env`, so the documented `docker build` baked the operator's checked-out repositories and a root `.env` into the image. It now excludes everything and re-admits only the build inputs (manifests, lockfile, `packages/`, `runner/`, `scripts/`, licence files), with `node_modules`, `dist`, `.gaffer`, `.git`, `repos`, `.env*`, databases and key files excluded inside them too. `scripts/docker-context-check.mjs` evaluates the file with Docker's matching rules against the tree and a list of hostile probe paths and fails on any of them or on a missing build input; CI runs it, and `runner/test/docker-context.test.mjs` covers it.
- **An unapproved memory draft is invisible to other agents in every read path (external review #7).** A second agent found a draft through `suggest_lore`'s duplicate feedback and fetched its full text by id with `get_lore`. In factory context the duplicate feedback now considers active records only, `get_lore` answers a draft id exactly like a missing one, and `report_conflict` refuses it as unknown; `search_lore` already ignored drafts there. See `packages/memory/CHANGELOG.md`.
- **Webhook URLs are secrets: no principal reads them from the settings list (external review #5).** A read-only API token retrieved the complete Slack and generic webhook URLs, env-backed and file-backed, from `GET /api/settings`. Settings now carry `secret: true` in `SETTING_DEFS` (both notify URLs; new secret keys inherit it), and the list reports such a key as `configured` plus the URL's `host` with an empty `value` / `effective` to every principal. Only an admin principal reads a value back, through `GET /api/settings/secret/:key` (403 for a read token or a human principal). The Settings view shows a masked field ("Set · hooks.slack.com") with Replace and Remove, and never sends an untouched secret. Covered by `api-settings-secrets.test.ts`, `web-settings-secret.test.ts` and a UI-regression step.
- **An approval covers only the commit the reviewer saw (external review #2).** The Review view showed diff A; the branch advanced to B before the click; `POST /tickets/:id/review/approve` returned 200 and pinned B, because the dashboard sent only the ticket id and the server read the head at approval time. The diff endpoint now returns each write repo's `repoId` and `headSha` (and diffs exactly that commit); the dashboard sends them back as `commits`; `ReviewGateService.approveReview` refuses with `409` (`details.reason: stale_revision`) when any head differs, or `revision_required` when no commit is named, and records the approval and one pin per repo in one transaction. The Review view says the change moved and reloads the new diff. `wg review approve --commit <repo>=<sha>` is required (`wg ticket diff <n> --heads` prints the values), `gaffer approve` shows the commits and asks, and the runner's agent review names the commit its reviewer judged (a multi-repo ticket, whose other repositories that reviewer did not read, is held for a human). Covered by `packages/dispatch/test/review-stale-revision-landing.test.ts`, `web-review-stale-revision.test.ts` and a step in `scripts/ui-regression/regress.mjs`.
- **The pre-gate dependency install runs inside the validation sandbox (external review #1).** `--ignore-scripts` does not stop a package manager running repository code: pnpm loads a repository's `.pnpmfile.cjs` on every install. With a validation wrap that refused all execution, a delivery's `.pnpmfile.cjs` still wrote a file outside its worktree, holding an operator token from the runner's environment, before any human review. `gaffer_dod_install_deps` now runs through `GAFFER_DOD_WRAP` with the `validation` profile, in a stripped environment (`env -i`: `PATH`, a throwaway `HOME`, `TMPDIR`, locale, proxy and CA settings only). Under `GAFFER_STRICT_REQUIRE` an install with no wrap is refused and logged, and the host-side primary prime (`gaffer_ensure_node_modules`) is skipped. Covered by `runner/test/dod-sandbox-wrap.test.sh` and a marker step in the docker containment gate.
- **A passing test can no longer delete the checkout it ran from.** Runner tests created their temp dir with `WORK="$(mktemp -d …)"`, often canonicalised it with `cd "$WORK" && pwd -P`, and removed it with `trap 'rm -rf "$WORK"' EXIT`, with no failure check. When `mktemp` failed (a missing or full `TMPDIR`), `WORK` became the current directory: orphan-recovery wrote its fixtures into the checkout, reported 11 passing checks, and its trap removed the checkout's `.git`. ## [0.1.0] - 2026-06-17

### Added

Initial public release of Gaffer — a local-first, supervised software factory.

**Dispatch** (`packages/dispatch`) — the control plane. Manages tickets, epics, scopes, and per-repo access. Exposes a REST API, an MCP server, a web dashboard, and a CLI. Enforces the server-side review/merge gate: by default, an agent actor cannot approve or merge its own work.

**Crew** (`packages/crew`) — the factory runtime. An MCP tool server that exposes factory-level tools to Claude agents, plus a hooks engine and idle loops for drafting work, ingesting issues, and repo onboarding.

**Memory** (`packages/memory`) — durable, human-gated knowledge. A knowledge base (lore) plus the Repo Understanding engine: Repo Digest, feature ledger, and grounded lore drafts. Seeded at onboarding; refreshed as tickets merge. Also usable standalone as `memory-mcp`.

**Runner** (`runner/`) — the bash orchestrator. Spawns a `claude -p` agent per ticket with a 66-skill library. Includes a deterministic PreToolUse safety hook (`safety-hook.mjs`) that scopes writes to the per-ticket git worktree and fails closed. Model tiering: planning on a strong model, implementation on a fast one. Per-call resource caps (wall-clock timeout + agent turn cap).

**Web dashboard** — seven views: Overview, Work, Review, Epics, Map, Memory, Settings. Review is the human gate where tickets wait for approval before any merge occurs.

**Safety boundary** — worktree isolation (every ticket in a throwaway git worktree), deterministic regex-based safety hook, server-side human review gate. Autonomy flags (`DISPATCH_ALLOW_AGENT_APPROVE`, `MERGE_ON_AGENT_REVIEW`, `MEMORY_AUTO_APPROVE`) are opt-in and off by default.
