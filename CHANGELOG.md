# Changelog

All notable changes to Gaffer are recorded here. The format is based on
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project follows
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Every package moves on one version train (see [docs/RELEASING.md](docs/RELEASING.md)).
Before the monorepo, memory-mcp shipped on its own as 0.1.0, 0.1.1 and 0.2.0
([its log](https://github.com/tmj-90/gaffer/blob/28475dc/packages/memory/CHANGELOG.md));
its `package.json` still says 0.2.0 from then, and the next release sets every package
to the same version.

## [Unreleased]

### Review

- **The review packet.** The Review view puts the runner's facts above the agent's words: what the ticket asked for, the gates and the tester's verdict as the runner recorded them, and whether the commit on screen is the candidate that passed.
- **A Behavioural surface panel above the diff** says what a change touches, and lists the callers and tests of each symbol it changes, read from the new code index.
- **Review comments, Fix these, and changes since your review.** Comment on a diff line, a file or the whole change (in Review, with `wg review comment` or over REST), mark each Must fix or Consider, and see the next attempt as the change since your review instead of the whole diff again.
- **Repeated review feedback becomes a proposed rule.** When the same send-back reason or must-fix comment appears on three tickets in a repository, Gaffer drafts it as a repo-scoped convention you approve (`wg review-rules` lists them). Only a person's feedback seeds a rule, and a rule draft never auto-approves.
- **An approval names the commit you saw.** Every approval pins the reviewed commit of each write repository and is refused (`stale_revision`) when a branch moved after the diff was shown.
- **An approval covers every write repository.** While any write repo's delivery head cannot be resolved, approval is refused for humans and agents alike, and a multi-repo ticket is done only when every pinned commit has landed.
- **The reviewer is never the author.** The control plane refuses an agent's approval when it holds the ticket's latest claim, whatever the autonomy flags say.
- **Gate integrity: a delivery cannot pass by weakening its tests.** The runner records the commit each delivery branch was cut from, runs the gate scripts as that commit has them, and flags deleted, renamed, skipped, emptied or gutted tests, changed test-runner config and package-manager rc files. Dispatch recomputes the check from the real diff and holds an agent's approval for a human; only a human can allow test changes. It flags, it never fails a delivery.
- **Machine-checkable acceptance criteria.** A criterion can carry a `check_command` the runner executes byte for byte as stored; the done gate refuses one the runner has not passed.
- **Editable Definition-of-Done commands.** Set a repo's test, lint and coverage commands from its page or with `wg repo set-commands`; onboarding detects them.
- **A red tests gate under a worker pool is rerun once at concurrency 1** before the attempt counts, so a test that races for a port no longer parks a correct delivery.
- **A security second-opinion reviewer.** After the primary reviewer approves a high-risk ticket, or one touching a security-sensitive path, a second agent reviews it against the security checklist (`GAFFER_SECURITY_REVIEW=0` turns it off).
- **Required CI controls approval and fails closed.** With `GAFFER_REQUIRE_CI`, approval, a tester PASS and landing need a recorded PASS for the exact commit; a gate that cannot read CI no longer reports success.
- **The sign-off says what Approve will do**: send to the tester, wait for Merge now, or merge, and whether every write repo lands.
- **The autonomy ladder, with automatic step-down.** Every repo x risk x gate shows its rung (a person decides, suggested, automatic), the evidence behind it and the distance to the next rung (`wg autonomy ladder`, `GET /api/autonomy/ladder`). A regression linked to an automatic change, a person reopening an automatically landed one, or two tester FAILs or unprovable holds on automatic approvals within 30 days take autonomy back for that row at once (a merge step-down also covers every higher risk), stop a landing already under way on an agent's approval (and an agent's approval still waiting to land), and restart the suggestion's count. A change a person approved is not counted against the merge gate and is not held by a step-down; a held landing says how a person lands it. Only a person lifts it (`wg autonomy lift`, `POST /api/autonomy/lift`); the safety hook refuses the command to agents and MCP has no such tool.
- **Tickets and their criteria can be edited until they are claimed** (`wg ticket edit`, `wg ac edit`, `wg ac rm`); from claimed on the contract is frozen (`CONTRACT_FROZEN`).

### Tester

- **The tester tests before you review.** When the independent tester gates a ticket, it runs before the human review, and approval of a commit it has not passed is refused. With `GAFFER_TESTING` unset, it gates a ticket when every write repo has a registered test command.
- **Acceptance profiles.** A CLI or API change can be accepted only after the runner ran the commands or probes a person registered (`wg ticket acceptance-profile`), in a fresh checkout of the tested commit.
- **Every epic has an acceptance ticket** the tester must pass, and an epic reads accepted only when the tester's assertions passed on what actually landed.
- **The landing replay runs the registered test command** with the tester's files appended, and the tester's PASS binds the named tests the runner's own replay saw pass: a skipped, missing or failed one holds the landing.
- **Accepted means verified.** An automated PASS needs a passed replay of the tested commit and contract; a PASS the runner could not replay is held for a human.
- **The tester gets the requirements it verifies**, its verdict is bound to the code and contract it tested, and it can no longer advance the reviewed delivery branch.
- **A tester FAIL is a bounded rework** in autonomous mode, not a silent stop, and a reworked ticket is tested again in the same run.
- **"This cannot be proven on this host" is a hold for a person, never a FAIL and never a PASS.** The tester may end with `{"verdict":"UNPROVABLE","criteria":[...],"needs":"..."}` for criteria the host cannot show (no browser, say) after trying another way. Every other criterion is still proven by the clean replay, and a failing replay or criterion is still a FAIL. Otherwise the ticket is held in testing with the code `tester_unprovable`, the criteria, the reason and the tested commit, on the ticket page, in `gaffer status`, `wg stats` and the factory log, in every posture: nothing is reworked, reviewed, approved or merged on it, and it is not tested again on the same commit. A person records the tester verdict, or a new commit is tested afresh. A malformed token is a plain hold. Tester verdicts are counted with these holds apart.
- **A test contract can declare what its proof needs from the host** (`wg ticket test-contract <n> --needs browser`; a closed list, an unknown name is refused; only a person declares or changes it, never the agent delivering the ticket, and the hold names who declared it and when). The runner probes the host itself; when a declared capability is missing the tester is told, and its outcome is the same hold for every criterion.
- **Planned tickets reach the tester with a test contract**, and while the tester is on, a planned epic's implementation tickets are created testable.
- **What you agree while planning is tested.** Each answer you give the planner becomes a criterion of the epic's acceptance ticket, and the proposal flags any answer no criterion covers.

### Landing

- **The merge gate.** "Done" means the merge of the approved commit onto the current target passed the gates; every landing path lands exactly that commit while the target is unchanged, and holds a red combination for a human.
- **A merge lane.** What is approved lands, whoever approved it, and a merge conflict no longer ends an autonomous run: the resolver's commit is gated again before re-review.
- **Provenance trailers** (`Gaffer-Ticket`, `Gaffer-Reviewed-By`, `Gaffer-Gates`) on every merge commit; `GAFFER_PROVENANCE_TRAILERS=0` turns them off.
- **Landing never overwrites a file you ignore locally**; the ticket is held with the file named.
- **A cancellation or a red required check stops every landing not yet started**, and one that had started is reported, never read as a clean merge.
- **PR mode merges through the PR.** Every recorded pull request must land upstream before a ticket is done, and a failed PR merge holds the ticket instead of landing locally.
- **A partly landed ticket can only be finished**, never cancelled, and a multi-repo ticket whose branch moved since review lands nowhere.
- **Teardown removes only what the run owns**, so a stopped or expired worker cannot delete its replacement's branch.

### Scout and routing

- **A pre-work scout** tells the delivery agent where a change likely lands and can raise a ticket's risk. The deterministic scout is always on; the model scout is opt-in (`GAFFER_SCOUT=auto|on`) and read-only.
- **The reviewer and clarify passes are routed** by the same tier router as delivery, and every attempt records the model it asked for and the CLI version.
- **Skills follow the role, the stack and the paths a job touches.** Each agent gets its role's skills for its repo's stack, a mixed repo routes per path, a two-repo ticket gets each repo's stack, and the ticket text can pull in a matching skill.
- **Every bundled skill rewritten against primary sources, behind a lint gate**, mounted beside a repo's own `.claude/skills` where the agent CLI looks.
- **An opt-in live test** checks that the agent actually uses the skill Gaffer chose (`GAFFER_LIVE_SKILL_TEST=1`).
- **Every delivery attempt leaves a replay manifest** (`$GAFFER_DATA/manifests/<ticket>-<n>.json`): repos and commits, the router's decision with declared and effective risk, the settings that shaped the attempt, hashes of the prompt and scout packet, the ledger join key and the outcome. Credentials in a test command are redacted and a write failure never holds up a delivery.
- **A routing scorecard** (`wg stats routing`, `routing_scorecard` in `/api/health`, a Health card) splits attempts, submissions, rework, first-pass acceptance, attempts and cost per accepted change, escaped defects and tester false greens by provider, model, role and work class. Every figure shows its n; cells under 10 read "too few to compare"; nothing is ranked and there is no overall score.
- **Matched experiments.** `gaffer eval experiment` delivers the same tickets under two or more arms of settings through the real worker seam and gates and reports paired differences with intervals. The default stub agent is free and runs in CI; `--live` runs the real agent under a hard USD cap, a ticket cap and the factory's budget admission and usage pause, and records nothing to dispatch.
- **Advisory routing recommendations.** `wg routing recommend` prints a proposed `model-registry.json` diff with the evidence behind it and never edits the registry; nothing is proposed for the reviewer or the tester. You apply a proposal by editing the registry.

### Memory and index

- **A code index.** `memory index build | neighbours | stats` maps a repo's TypeScript, JavaScript and Python files, symbols, imports and tests, incrementally and within caps; it answers which files and tests import a path or symbol.
- **Hybrid lore retrieval.** Search fuses full-text ranking with a dense vector per record, so a typo or a synonym still finds the record.
- **Lore version history.** Every update snapshots the previous version; `memory history <id>` lists them.
- **Lore drafts are ratified from the dashboard** (and `gaffer lore`), not only from the memory CLI.
- **Unapproved drafts are invisible to other agents** in every read path, and the requirement the runner distils from a delivered ticket is a draft unless `MEMORY_AUTO_APPROVE` is on.
- **Spec-freeze lore, agent drafts and onboarding lore reach delivery agents** once approved.
- **The index describes the merged commit.** After overlapping merges memory refreshes from the merged tree and verifies the file cards (`memory card verify`) before recording a repo as indexed; summaries survive the refresh and a rename.

### Dashboard

- **Match Day.** The dashboard is now a football manager's match day: a scoreboard and Team sheet of what needs you on the Overview, a Tactics board, the Squad with a named club and agents (name, shirt number, kit colours), a claret header with live counts, and light and dark from one token set.
- **The Floor** (`#/floor`): a live factory floor with one parcel per open ticket and a robot on every live claim.
- **Health** measures human review time, first-pass acceptance, flow efficiency from agent-working time only, rework including review send-backs, escaped defects you link to the change they escaped from, and what each judging lane said.
- **The four quality measures carry a period, the period before and a history.** First-pass acceptance, human review time, the cost per accepted change and the escaped-defect rate each say which window they cover (`window_days`, null for all time); `GET /api/health?window_days=N` applies one window to all four (and governance), and without it each keeps the window it had. Each serves `previous`, the same figures over the equal window before, and twelve ISO weeks of history (`by_week`; the escaped-defect rate six monthly cohorts in `by_month`, the recent ones marked `maturing`). An empty week or month is present with a zero count and a null value, never a zero rate or the week before's figure. Beside each escaped-defect rate, `upper_95_pct` says how high it could still be (0 of 11 accepted changes could be up to 25.9%). `wg stats` names each figure's window, the escaped-defect rate's window before and, at zero, its upper bound.
- **The cycle-time series no longer invents values.** A day with no completion is null in `cycle_time.series` (it used to repeat the day before, and read 0 before the first completion), `cycle_time.series_n` gives the completions behind each day, and `p75_days` and `p90_days` sit beside the median. The Form guide's cycle chart draws no bar on an empty day, its sparkline joins only the days with a completion, and the Lead time sparkline skips a day whose trailing week had no completion instead of dropping to 0.
- **A live event stream** (`GET /api/events/stream`) keeps every view current without polling.
- **The Team sheet** lists paused deliveries, lore drafts and the dependents of a cancelled or failed ticket.
- **A read-only token sees no live write control**, and the login gate sends no data call it cannot have.
- **Fonts are self-hosted** and the CSP allows no third-party origin.
- **Accessibility and layout.** Every form label is associated with its control, the palette, More menu and Floor work from the keyboard, and no view scrolls sideways at phone, tablet or desktop widths.
- **The board has no ticket ceiling**, and the Map, Overview and Epics read ticket details in batches.
- **One set of shared parts for numbers, charts and tickets.** Durations read one way ("2d 3h", "9h 16m", the Team sheet included), money never shows four decimals, and a percentage carries its "%" with no gap. Charts read time, never categories: a sparkline needs four real points on an even time grid, breaks at a missing day instead of drawing a zero, and reads out a point on hover and from the keyboard; the Health cycle-time chart caps its bars at 24px, picks minutes or hours when the cycle is short (no more "0.0 days") and has a *Show as table* view. Rates show their count and a likely range (a 95% Wilson interval) and grey out under ten. On Health the code index is a table and its callers share a measure tile, and the pre-work scout shows what each attempt started with as a bar and first-pass by arm as rows with their counts. On the Work board the ticket title is louder than its number; a waived tester verdict on the ticket page reads as a callout; acceptance criteria carry a verdict mark instead of a ticket's lifecycle glyph; the Team sheet says a parked ticket's reason in words (the server's code stays in its tooltip).
- **One colour vocabulary.** A club colour within OKLab 15 of the referee's yellow, red or pass green no longer paints blocks, the header hoop, washes or the phone browser's bar: they keep the house claret or sky, the shirts and crest keep the club's colour, and *Name your club* says in one line which colour gave way and why. Charts never wear the kit: bars, sparklines and meters use their own validated chart colours, with steps for light, dark and the scoreboard. Dark mode has its own deep sky blocks, mid-grey card frames and a lit outline round the Work board instead of the light colours flipped. Unsaved settings, the Go / No-Go advice and the review strip's "worth a look" cell no longer use the yellow card, which now means only "needs you". The Floor's stations are re-stepped so neighbours are easy to tell apart (in colour-blind vision too), and Inspection moves from red-pink to violet-magenta, clear of the status red; Assembly (and the robots' hard hats) stays orange in dark mode rather than drifting toward red.
- **Health tells the quality story first.** The four measures are the scoreboard: a tile each with its count, the window it covers, the change against the window before (shown only when both have at least 10), a weekly or monthly sparkline in UTC weeks and months, the 95% interval for a rate and what it counts behind a disclosure; the Referee's record window select sets all four (the newest choice wins, and a read that fails keeps the window showing and says so), and a sparkline's readout names the UTC week, month or day. Under them, what is behind each one (who approved, waiting to be opened against deciding, where the spend went, the monthly cohorts with the maturing ones marked). The routing scorecard, what each lane changed and the code index are tables; the scout arms, skill hit-rate and recall are rate rows and segmented bars, with counts in grey under 10. The ledger figures that filled the scoreboard are one quiet row in "Where the wages go" (the cost per shipped ticket is gone: the accepted-change cost is the price), a missing figure is a dash with its reason, and the Form guide drops its client-side Lead time and Deployments cells, labels UTC days and says its chart is the daily mean.
- **`GET /api/health?view=summary`**, the Overview's lighter read: the ledger figures, the event log and the accepted-change cost without the review measures, routing, scout, code index, skills or recall (about a third of the full read's time on a 10,000-ticket factory). `cycle_time.median_days` is null when nothing has shipped, never 0.
- **Review and the ticket page lead with the decision.** On Review the sign-off (Approve, Fix these, Send back) is on the first screen of a 1440x900 window, under one compact row of verdict cells (a label, a pass/fail/flag mark and one word each, the detail behind a disclosure), and the sections below it are on the one heading scale. On a phone the three sign-off actions stay in a bar above the tab bar. Review and the ticket page share one ticket header (the title first, the number and status under it, the yellow card only when the ticket waits on you); gates, criteria and tester verdicts use their own marks, warnings and banners one callout style, the side stripes are gone, and reason codes read in words. The packet's cost shows what an accepted change typically costs, a done ticket's time shows the factory median, the Review desk says how long a change waits before you open it, and a ticket's runs are a table. What Approve requires is unchanged.

Ticket numbers, priorities, tables (Epics, the Map register, the League table), bars and empty lines on the other views use the shared parts, campaign names wrap, and a view leads with at most two block heads, claret only where you act. - **Every dashboard image in the docs comes from one script.** `node scripts/screenshots.mjs` builds a demo world on the browser harness, works its tickets through the live path with the stub worker (no model is called and nothing is spent) and rewrites `docs/img`; `--reuse --only <names>` recaptures a few shots. The stub worker gains scripted deliveries for it (`steps`, `tester` and `observation`), and a caller that sets none of them sees no change ([docs/testing.md](docs/testing.md#screenshots-scriptsscreenshotsmjs)).

### Runner and sandbox

- **A whole delivery through the docker sandbox is tested in CI**, and a live one is a workflow you run on your fork ([docs/sandbox.md](docs/sandbox.md#prove-it-on-your-own-fork)).
- **The docker sandbox holds no database.** The dispatch and memory MCP servers run on the host behind a per-spawn socket, the container gets a private git dir and the host imports only the ticket branch, and a repository cannot add a host directory to the mounts.
- **Validation runs inside the agent's sandbox**: the DoD gates, the criterion checks and the pre-gate dependency install, with no data plane and no model credential.
- **Autonomy requires containment.** Every ship flag, `GAFFER_AUTO_PUSH` included, defaults `STRICT_MODE=1` and `GAFFER_STRICT_REQUIRE=1`, and every agent spawn goes through the one containment seam.
- **`SANDBOX_PROVIDER` auto-detects the host**: `sandbox-exec` where it exists, `docker` where only the Docker CLI does. The `lima` stub is removed.
- **A second worker provider: your own program.** `GAFFER_WORKER_PROVIDER=command` runs a program under [a documented contract](docs/worker-providers.md), only inside the docker sandbox with the bridge, with its cost booked at no less than a per-call floor.
- **The safety hook judges a command as the shell would run it**, refuses a control-plane verb it cannot read off the command line, fails closed on oversized input, blocks a timed-out or crashed hook's tool call, and blocks the package-manager commands that rewrite the shared `node_modules`.
- **The runner's own git never runs a repository's hooks or drivers.**
- **A live run needs a dollar cap.** `gaffer run`, the loop, Poll for work and every other paid launch refuse to start without `GAFFER_DAILY_BUDGET_USD` or `GAFFER_BUDGET_USD` (`GAFFER_ALLOW_UNCAPPED=1` opts out, from the environment only); the cap fails closed when spend cannot be measured.
- **A usage limit pauses the factory** instead of burning attempts, and only the CLI can report one.
- **Waste controls.** A delivery stopped by a cap or timeout keeps its work, the rework loop stops when an attempt repeats the previous failure, and prompts carry a turn and output budget.
- **The idle maintenance lane closes its loop** and can be switched on from the dashboard.
- **A greenfield run needs no first-run steps**: the factory handles the proxy CA, an offline npm cache, the tester flags and a repo with no remote.
- **Execution preflight probes the package registry** from the agent's own environment.
- **One-command container run.** A root `Dockerfile` and `compose.yaml` start the dashboard and runner (`docker compose up -d`); bootstrapped repos survive a container recreate.
- **The runner no longer needs python3**, and its text processing runs through one typed renderer.
- **`runner/tick.sh` is orchestration only.** Its phases (admission and claim, launch, the delivery gates and the submit / rework / park decision, the close path, idle work, crash recovery and resume, the greenfield bootstrap) moved verbatim into `runner/lib/tick-*.sh`, which `tick.sh` sources up front and will not run without; no behaviour changed.
- **The runner's config is split by area.** `runner/factory.config.sh` is now a short file that sources `runner/config/NN-area.sh` in a fixed order and stops when a part is missing or did not load whole; no knob, default or precedence changed.
- **CI costs about half on a push that leaves the runner alone.** The macOS runner shards run on a push or pull request only when it changes a path that can behave differently on macOS (`runner/**`, `scripts/**`, `.github/**`, the package manifests, the lockfile, the Node pin; Markdown never counts), and the runner tests on Node 24 run nightly (the package tests on Node 24 stay on every push). The nightly workflow runs every cell a push may leave out, `workflow_dispatch` on it runs the full matrix by hand, and one always-running `CI result` check is the one a branch rule can require ([docs/testing.md](docs/testing.md#what-ci-runs-and-when)). No runner test file runs longer than 150 s at `-j 2` any more: the eight slowest are split on their independent sections, each half on its own world, with every check kept.
- **A delivery tick starts about 60 node processes, not about 150** (about 4 s of process start-up instead of 17 s with a stub agent). Each tick runs its dispatch CLI calls (`wg`) through one long-lived dispatch process and its JSON helper calls through one long-lived JSON process, over private named pipes that answer only their own tick (a per-tick key held in the tick's memory, never on disk or in the agent's environment), with the same code, output and exit codes as the one-shot calls, and reads several fields of one ticket view in one helper call. Anything a server cannot run identically goes one-shot; a dispatch server that dies, hangs or answers garbage fails that call closed, and the rest of the tick runs one-shot. `GAFFER_WG_SERVE=0` turns both off for troubleshooting.

### CLI and API

- **One front door.** `gaffer wg`, `gaffer approve`, `gaffer merge`, `gaffer plan "<goal>"` and `gaffer lore` cover the first run from the terminal; `gaffer onboard <path> --name <alias>` onboards under an alias.
- **Named principals.** `dispatch principal create <name> [--read] [--admin]` (or Settings, Access) mints a credential bound to an identity, optionally scoped to repositories or tickets; the CLI acts as one with `GAFFER_PRINCIPAL_TOKEN`. Repository-level writes need an admin principal.
- **Every data-returning request needs the bearer token**, reads on loopback included.
- **`wg block` and `wg unblock` for people**, and `wg ticket create --repo <name>`.
- **`wg` speaks to a person.** Usage errors exit 2, every failure is one JSON error line with a message you can act on, `--json` works everywhere, and a board command starts faster.
- **`dispatch repo list`**, and `gaffer status` lists the registered repos and the autonomy posture.
- **`gaffer dashboard --stop`**, a `--restart` that restarts, and "up" only when its own server answers.
- **Tamper-evident event log.** Every event is hash-chained (`dispatch events verify`) and carries the tick that wrote it.
- **An OpenAPI 3.1 contract** at `GET /api/openapi.json` and [docs/openapi.json](docs/openapi.json).
- **A generated configuration reference**, [docs/CONFIG.md](docs/CONFIG.md), checked in CI.
- **Gate replay and an eval ledger.** `gaffer eval replay` replays recorded deliveries through the real gates, and `gaffer eval agreement` measures whether the opt-in judge agrees with reviewers ([docs/eval-harness.md](docs/eval-harness.md)). `gaffer eval` now labels its old "memory lift" figure as the *memory score gap*, since it compares different tickets and proves no uplift.
- **A release pipeline.** A `vX.Y.Z` tag builds, tests and publishes tarballs, an SBOM, checksums, a provenance statement and the image ([docs/RELEASING.md](docs/RELEASING.md)).
- **`dispatch export` is a consistent snapshot** that proves it restores, and a rejected restore leaves the previous state intact.

### Security

- **The safety hook judges a relative path from every directory the shell may be in.** It followed `cd` with one directory and moved it at every `cd`, whatever context the `cd` ran in, so `cd <read-only dir>; (cd <worktree>); python3 -c 'open("x","w")...'` was judged as writing into the worktree and wrote into the read-only directory; a skipped conditional, an uncalled function, a `cd` in a pipeline or a background job, `cd X || true`, `false && cd X`, a `cd` that fails, `eval cd`, a trap and a loop gave the same kind of wrong answer, for inline programs, for plain Bash writes (redirections included) and for relative reads. Now a `cd` in a subshell, pipeline, background job, coprocess, block or conditional only adds its directory, a `cd` may fail (only a command joined to it by `&&` runs with it done), and a loop, function, trap or alias that changes directory leaves the directory unknown; a relative path is allowed only if it is allowed from every directory, and an unknown directory refuses relative inline writes and reads.
- **The safety hook's directory tracking covers what runs later or elsewhere.** An independent review of the fix above found the real shell in a directory the analysis did not hold: a function, trap, alias or redefined `cd` that runs after a later `cd` the hook followed (`f() { cd /ro; }; cd <worktree> && f && touch x`, `trap 'cd /ro' DEBUG`), a command named by an expansion (`C=cd; $C /ro`, `f() { "$@"; }; f cd /ro`), `trap "$T"` / `eval "$T"`, `cd -P link/..` and `set -P`, `/proc/self/cwd` (resolved in the hook's own process), CDPATH set under a name the hook did not see, variables assigned in a subshell, pipeline, function, loop or by `printf -v` / a nameref, `env -C`, `find -exec` / `-execdir` commands, a `cd` in a body xargs fills in, and the writes only the segment extractor knows (`sed -i`, awk redirects, `rsync`, `curl -o`, `git clone`), which kept the old single-directory replay. Each is now refused; no command bf5e305 refused is allowed.
- **Autonomy policy rows, ticket risks and lifts of a step-down count only with a signature under the factory key (upgrade step: re-sign your automatic rows).** A process that could write the sqlite file used to grant itself automatic approval and merge by inserting an `autonomy_policy` row, lowering a ticket's `risk_level`, or appending a lift event. Now a policy row is honoured only with a seal (`setAutonomyPolicy` writes an `autonomy_policy.enabled/changed/disabled` event and the seal in one transaction), an unsigned risk is decided as the highest (a person decides; hold `autonomy_risk_unsigned`), and a lift without a seal is ignored; a deleted step-down does not lift. A key holder seals a ticket's risk at creation (`ticket.risk_set`); a ticket created through MCP or by the planner is sealed at its first claim by the host, at the risk its creation recorded (a risk lowered before the claim is left for a person to re-sign); a step-down lands on the signed risk (an unsigned one steps down every level). A verified chain checkpoint beside the anchor keeps one decision in a fresh process at about 12 to 18 ms on a 100k-event log. **Upgrade step: nothing is signed automatically.** Existing automatic rows are off until you review them (`gaffer wg autonomy unsigned`, Settings > Autonomy, `dispatch doctor`) and re-sign them (`gaffer wg autonomy resign <id> --confirm <review_code>` or `--all --confirm <code>`); tickets already in flight are decided as the highest risk until you re-sign them (`gaffer wg autonomy risk-unsigned`, then `risk-resign --all --confirm <code>`). Re-signing is refused for agents, the runner, read-only, scoped or non-admin principals and MCP; the safety hook refuses `autonomy resign` and `autonomy risk-resign` to agents. New: `GET /api/autonomy/signatures`, `POST /api/autonomy/signatures/resign`, `GET /api/autonomy/risk-signatures`, `POST /api/autonomy/risk-signatures/resign`.
- **The safety hook judges inline programs by what they can do, not by how a write is spelled.** Its inline-interpreter rule was a list of write calls, and an independent review got past it with numeric open flags (`os.write(os.open("/etc/x", 65), b"x")`), a keyword mode (`open(p, mode="a")`), escaped quotes in a double-quoted `-c "..."` program and `f.writeSync(f.openSync(p, 1))`: with `SANDBOX_PROVIDER=none` that was a write anywhere the operator can write. An inline program (`python -c`, `node -e` / `-p`, `deno eval`, `bun -e`, `ruby -e`, `perl -e`, `php -r`, and the same fed on stdin, also behind wrappers, `xargs`, `sh -c` and `eval`) is now read as the interpreter receives it, lexed per language, and refused when it can write or delete files, start a process, reach the network or run code built at run time, under any alias or spelling; the only capability allowed is a write whose every path is a literal inside a write root, and that path now gets the checks a Bash write target gets (an inline write to `.claude/settings.json` or `.git/hooks/` passed before). A program the hook cannot see (a command substitution, an xargs placeholder, a variable set at run time, a program piped from `curl`) is refused. Programs inside `$(...)`, backticks, process substitutions and `trap` are read too; interactive modes reading stdin (`python -i`, `node -i`, `php -a`, `perl -d`), preload variables (`NODE_OPTIONS=--require`, `PERL5OPT`, `RUBYOPT -r`, `PHPRC`, `PYTHONSTARTUP`, `LD_PRELOAD`), `node --import data:`, `php -d auto_prepend_file=` and `deno run https://` are refused; variables that run code for any command that reads them (`NODE_OPTIONS` with a `data:` module in front of `npm test`, `PS4` with a substitution, `GIT_CONFIG_*`, `GIT_SSH_COMMAND`, editor and pager commands, `MAKEFLAGS` carrying make text) are refused in front of any command; a standard-library `python -m` command line is read (`-m timeit` code as a program, `-m json.tool` / `-m venv` / `-m py_compile` outputs as writes, `-m http.server` only on the loopback interface); awk, sed and sqlite3 programs are read for commands, reads and writes with their options as GNU reads them, the sqlite3 database file is judged as a write, make's command line is read for `--eval`, stdin makefiles and assignments it expands, and inline lua, R, osascript, tcl, expect and dc programs are refused. A command the hook cannot lex is refused (bash runs the lines before the one it cannot parse), and the Bash write targets of one command are judged once each within the rule budget (thousands of repeated targets took 40 s). 790 harmless commands stay allowed and 544 hostile ones are refused (`runner/test/safety-hook-inline.test.mjs`). A program file the agent writes and runs is still not analysed (SECURITY.md).
- **The safety hook judges a write inside a compound command.** Its Bash write-target extractor split a command on `;`, `&&`, `|` and newlines and took the first word of each piece as the verb, so a write behind `(`, `{`, `if`, `case`, `exec`, inside `$(...)` or backticks, or in an `eval`, `trap` or `echo ... | sh` string was never judged: `(touch /etc/x)` and `x=$(rm /etc/hosts)` were allowed, and with `SANDBOX_PROVIDER=none` that is a write anywhere the operator can write. The expansion walk the read boundary already used for those shapes (loop variables, `cd`, substitutions, eval and `sh -c` bodies) now also collects the targets of the write verbs it reaches, judged like any Bash write target; a target it cannot expand is refused, as a variable in a top-level target always was.
- **Lock directories are taken atomically on every host.** The runner's directory locks (the review claim, the gate rerun lock, the poll lock, the takeover guard and the lock helper's fallback) relied on `mkdir` failing when the directory exists. The `mkdir` of uutils coreutils, the default on Ubuntu 25.10 and later, checks for the directory and then creates it, and reports success when it appeared in between, so two lanes could both take one lock (seen in CI: two lanes held one review claim). A lock is now taken by creating its pid file exclusively inside the directory, which only one process can do whatever `mkdir` reports.
- **Sign-in uses exactly the principal row it verified.** Sign-in read a principal by its token hash, then verified the seal of whatever row carried that id at a second read, and returned the identity and authority of the first. A process writing the database at the right moment (a forged row for the first read, the genuine row back for the second) signed in with authority no seal covered. The row is now read once, verified as read and returned as read, inside one read snapshot with its seal. The unsigned-principal review had the same shape: a row changed while the review was being built could be shown as one thing and carry the confirmation code of another; what is shown and the codes now come from one read of each row. A person's tester verdict checks the seal over the row it read. The event-log anchor, kept outside the database, is read before that snapshot opens, so a sign-in that overlaps another factory process's write is not taken for a truncated log and refused.
- **A custom settings template has to run the safety hook, not mention it.** The launch check recognised the mandatory hook by its path appearing anywhere in a PreToolUse command, so `true # node .../safety-hook.mjs`, `node .../safety-hook.mjs; true`, a background `&` and an `"async": true` entry all passed and blocked nothing. The command must now be exactly `node <runner>/safety-hook.mjs` (or the hook path alone) as one plain command, and the entry may hold only the keys the check knows; anything else is refused at launch. A template that sets `"disableAllHooks"` to anything but false, or `"allowManagedHooksOnly"`, is refused too: either switches the hook off without touching PreToolUse. The shipped template now quotes the hook path (a runner directory with a blank in it launches) and sets `"disableAllHooks": false`, so a `true` in the user's own Claude Code settings no longer switches the factory's hook off. `"onFailure": "block"` needs Claude Code 2.1.295 or later; an older one runs the tool when the hook times out or crashes.
- **A short glob can no longer stall the safety hook.** The hook's glob matcher was a regular expression (`*` as `.*`), and a pattern of many stars against one long file name (`cat src/*a*a*a...b`, 49 bytes, against a name of eighty `a`s) backtracked past the hook's timeout: the call was refused, but only after a minute of CPU. The matcher is now a walk bounded by name length times pattern length; the same command answers in the hook's normal time. A bracket range written backwards (`[z-a]`) is treated as syntax the hook does not model (it matches every name) instead of crashing the decision.
- **A long `declare`, `read` or `printf -v` or `node -e` can no longer stall the safety hook.** Whether a command may set `$NAME` in a way the hook does not follow was asked with one regular expression per variable name, which backtracked in the cube of the command's length: `declare -aaa…` of 6 KB with three variables, or 11000 `read` words with forty, kept the hook busy past its timeout. The names are now collected once per command by linear scans, with the same answers. The rule that refuses inline `node -e` reaching the control plane retried every later `node`, flag and package word (`node -e ` repeated to 63 KB ran the hook past three minutes); it is now one pass per line, with the same answers. And whatever is still slow (the command-position rules rescan a long word at every `{` inside it: 63 KB of `${` took about 100 s) is now cut off: past 10 s in its deny rules the hook refuses the command as unverifiable, inside Claude Code's 60 s hook timeout, so a Claude Code without `onFailure: block` never runs it unchecked.
- **A quoted `!` in a bracket no longer hides a secret from the safety hook.** The hook read `.[\!e]nv` and `.['!'e]nv` as "not e", matched nothing and judged only the directory, while bash expands both to `.env`: the file was read. A quoted `!`, `^` or `-` inside a bracket is now a literal, as in bash; under `nocaseglob` a range covers its folded endpoints as bash does, and a name with characters outside ASCII matches every pattern with `?` or a bracket (bash counts it in bytes or in characters, never in UTF-16 units). Compared with the real shell on generated patterns, the hook now matches at least every name bash does.
- **On macOS, sandboxed code can no longer change the factory's control files (a behaviour change).** The `sandbox-exec` profile used to grant writes to the whole of `$GAFFER_DATA`, so a script an agent ran, or a test a gate ran, could rewrite `settings.json`, clear the usage pause, truncate the ledgers or plant a skill, and the next runner process obeyed outside the sandbox. Writes there are now denied except for the dispatch and memory databases (with their SQLite files), the crew events log and the safety hook's two ledgers; the host's control files are denied by name as well.
- **`settings.json` sets only dashboard settings (a behaviour change).** The runner takes from it only the keys the dashboard's settings API can write; any other key (NODE_OPTIONS, BASH_ENV, DYLD_*, LD_*, PATH, CLAUDE_BIN, CLAUDE_FLAGS, GAFFER_IDLE_HOST_EXEC, GAFFER_DOD_SANDBOX, ...) is ignored and named on stderr. Set those in the environment.
- **The gates never run under the agent's sandbox profile on macOS.** The DoD gates, the acceptance checks, the pre-gate install and the merge gate get a fresh validation profile per run, with no `$GAFFER_DATA` grant beyond the worktree and no HOME grant.

- **The safety hook's own git lookups run without fsmonitor or hooks**, like the rest of the hook's git calls.
- **The macOS agent-config deny holds on a case-insensitive volume.** A new `~/.claude/CLAUDE.MD`, `Skills/` or `settings.JSON` is the file the CLI loads on the default macOS volume; those spellings, names holding a non-ASCII letter, each project's auto-memory directory and `$GAFFER_DATA` in another letter case are now denied too.
- **`GAFFER_DOD_ENV_PASS` never passes a loader or environment-control name** (NODE_OPTIONS, BASH_ENV, LD_*, DYLD_*, GIT_*, PATH, HOME, SSH_AUTH_SOCK, PYTHONPATH, ...), nor a credential spelled in lower case.
- **Docker's legacy layout masks a `settings.json` that did not exist yet.** With the MCP bridge off and no dashboard setting saved, the agent could create `settings.json` in the mounted data directory; the wrapper now creates an empty one first so it is masked like the other control files.
- **The safety hook no longer refuses a commit message or a search that only names a control-plane CLI, and refuses running git's stored text as a command (a behaviour change).** The control-plane rule matched `wg`, `dispatch`, `fg` or `crew` and a control-plane verb anywhere on a line, so `git commit -m "dispatch: reject bad events"`, `grep -rn "dispatch.*approve" src` and `echo "fg then approve" > notes.txt` were refused. A command the hook proves is data only (every segment a plain `git commit` / `add` / `status` / `diff` / `log` / `show`, `echo` / `printf`, `grep` / `rg`, `cat`, `ls` and the like, with no variable, substitution, backslash, pipe, newline or here-document anywhere) is now judged with the CLI in command position; every other command is judged as before, so wrappers, nested shells, `eval`, substitutions, `xargs`, pipes into a shell, `git -c alias` and multi-line commands stay refused. Since a commit message can now hold a CLI's words, running stored git text is refused: a command substitution as the program (`$(git log -1 --format=%s)`, unless it only finds a path such as `$(which node)`), `eval "$(git ...)"`, git output piped or here-stringed into a shell, and xargs running what git printed, also when the text is first put in a variable (`a=$(git log -1 --pretty=%B); eval "$a"`, `bash -c "$a"`, `echo "$msg" | sh`).
- **The safety hook reads a wildcard, a brace or a variable the way the shell will (a behaviour change).** A read operand with `*`, `?`, `[...]`, `{a,b}` or `$VAR` used to skip every read check, so in the production profile `cat $GAFFER_DATA/dashboard-*` printed the operator's REST token and `cp $GAFFER_DATA/mcp-r* src/x` copied the MCP claim token into the worktree. The hook now expands every read operand itself (the variables in its environment and those the command assigns, `~`, braces, and globs against the real filesystem, bounded and never through a symlinked directory) and judges each match like a literal path: a secret file, a path outside the roots, or a directory that holds or sits above the factory's secrets (`GAFFER_DATA`, the MCP config directory, HOME) is refused. An operand it cannot expand (a variable set by `read`, `$(...)`, `$((...))`, an xargs placeholder) is refused with a message to name the file; a glob with no match is judged by its literal directory; past a work cap the command is refused. The same check covers `<` redirects, `$(< file)`, `find ... -exec` start points, xargs-fed readers, `eval`, `sh -c` and command-substitution bodies, a relative operand after a cd the hook cannot follow, and recursive readers that follow symlinks (`grep -R`, `rg -L`, `find -L`, `cp -L`, `tar -h`, `rsync -L`, `zip -r`), and any word in any position that expands to a secret path (`cat $MCP_CONFIG`, `python3 $GAFFER_DATA/d*`) is refused unless the command only lists or removes it. Ordinary work is unaffected (`cat src/*.ts`, `grep -rn foo src`, `for f in test/*.test.js; do node "$f"; done`); `while read f; do cat "$f"; done` is now refused. The same review closed more ways around it: `$_` (the last argument, after `ls $GAFFER_DATA/dashboard-token`) is unknown; `..` is taken physically, so with a symlinked directory in the worktree `cat wt/../d*`, a Write or Edit to `wt/../settings.json`, a Grep rooted at `wt/..` and `echo x > wt/../settings.json` are refused (the tool paths and redirects were open on main too); CDPATH and extglob groups (`+(.)env`) are followed; `7z`, `pax`, `bsdtar`, `cpio -o` and `git grep / diff --no-index` are read vectors; and a loop or `xargs` that takes file names from a listing of `GAFFER_DATA` or HOME is refused whatever program reads them (`find $GAFFER_DATA -type f | while read f; do gzip -c "$f"; done`; `ls $GAFFER_DATA | while read f; do echo "$f"; done` is now refused too).

- **`gaffer dashboard` prints the login token only to a terminal.** The foreground (compose, systemd) path, the start and already-up paths and `--lan` printed the full `?token=` login URL (or the token and its QR) to stdout, so `docker compose logs` and any captured output kept the credential. - **Changes to the hook's rule modules count as security-sensitive.** The lite-mode classifier, the security second-review lane and dispatch's risk annotations match `runner/lib/hook/` and the deny list `runner/lib/dangerous-commands.mjs` as well as `safety-hook`, so moving the rules did not move them out of review. The deny list had never been matched: a change to it went through as an ordinary one.
- **Preflight loads the hook's rules.** `preflight.sh` now loads the hook's decision once, so a missing or broken `lib/hook` module or deny list shows as a failure there instead of as a hook that blocks every tool call.
- **Notifications are redacted and SSRF-checked by default.** Webhook and Slack bodies carry only the event kind, ticket number, status and dashboard URL unless you set `GAFFER_NOTIFY_FULL_PAYLOAD=1`. A sink URL must be http(s) and must not point at loopback, link-local or a private range unless you set `GAFFER_NOTIFY_ALLOW_PRIVATE=1`, so a LAN relay needs that flag now. The settings API no longer returns a webhook URL to any principal but an admin.
- **The container image's build context is an allow-list.** `.dockerignore` used to let `./repos` and a root `.env` into the image; now only the build inputs enter it. If you built an image from a checkout with either present, rebuild it.
- **Onboarding stays inside the repository.** A file that resolves outside the repo root (a symlinked README, say) is never read, and a password embedded in an https remote URL is stripped before it reaches a prompt, the digest, lore, events or logs.
- **The docker sandbox cannot move your branches.** The container works in a private git dir; only the ticket branch is imported back, and a gate run imports nothing.
- **The runner never writes through a link into an agent's worktree (a behaviour change).** Before an agent runs, the runner writes `.claude/settings.json`, the `.claude/skills` copies, `CLAUDE.factory.md` and `node_modules` links into its worktree on the host, outside any sandbox. A repository that committed a symlink at one of those paths (or made `.claude` a symlink) had the file it pointed at overwritten: external review 17 overwrote a file outside the worktree through a committed `.claude/settings.json` link in a full ticket run. Every such write now goes through `runner/lib/safe-write.mjs`, for the shell and Node launchers alike: a destination that is a symlink or not a regular file, or a parent below the worktree that is a symlink or not a directory, is refused, and the file lands by a rename in the checked directory. A refused delivery or bootstrap is parked `blocked` with reason code `unsafe_worktree_path` and a reason that names the path and the fix (replace the link with a regular file or directory, then `gaffer wg unblock <n>`); no agent is launched. A refused resume of a paused delivery goes back to `paused` instead, so its preserved worktree and uncommitted work are kept; the ticket names the link and the worktree. The review pass holds the ticket, the tester holds it in testing with the reason on the ticket, and the clarify pass and the merge resolver refuse to start, each with the same reason. A `node_modules` link whose parent is a symlink is skipped and logged. A repository that shares `.claude/skills` through a symlink now gets this refusal instead of a delivery without Gaffer's skills. The read side too: the tester's clean replay never reads a test file through a link (a link there fails the replay with the same reason, and the PASS is held), and the maintenance lane's idle scans never follow a link out of the repository into the draft tickets and lore they write.
- **One settings rule for every launcher.** The shell settings check used to look for the words `PreToolUse` and the hook path anywhere in the rendered file, so a custom template with the hook under another event, or a PreToolUse entry whose matcher covered no tool, launched shell-started agents that the Node launchers refused. Both now apply `runner/lib/agent-settings.mjs`: the settings must parse as JSON and run the safety hook as a PreToolUse command hook covering Bash, Write, Edit, MultiEdit, NotebookEdit, Read, Grep, Glob and LS, every entry with `"onFailure": "block"` and a timeout. The shipped template is unaffected; a custom template that covered only some of those tools is now refused by both.
- **Every agent spawn is checked for the safety hook.** The bootstrap, reviewer and clarify agents refuse to launch when their rendered settings do not name the hook, as delivery already did, and the macOS sandbox profile is written per call so concurrent workers cannot swap each other's write roots.
- **Dependency advisories.** The MCP SDK moves to ^1.32.2 and every package to zod 4 (GHSA-mrhx-c7xc-m3w5), and `fast-uri` to 3.1.6 or later (four SSRF and host-confusion advisories). REST and MCP validation errors keep their shape.
- **CodeQL and gitleaks run in CI**, and every action is pinned by commit.

- **The independent tester's prompt quarantines everything it did not write.** The ticket title, the description (the old REQUIREMENTS markers, which nothing escaped, are gone), each acceptance criterion and the test contract the delivery agent writes now sit in their own `<untrusted-*>` envelopes under the standard notice, so a hostile issue or an injected delivery agent can no longer close the block and tell the tester to answer PASS. An audit of every other prompt builder wrapped the raw fields it found: the eval judge's title and criteria, the greenfield repo classifier's title, description and repo purposes, and in onboarding the module names, repo commands, paths and the draft card under review; the clarify and product-owner prompts gained the notice. A rework failure trail that cannot be quarantined is left out instead of reaching the next attempt raw.
- **Every `<` inside an envelope is escaped.** The closing-tag neutraliser could be dodged with a soft hyphen, an invisible character inside the word or a look-alike letter; now every `<` of untrusted text becomes `&lt;` (idempotent; `&` is left alone) and every notice says "&lt; inside these tags is a literal <". One implementation per language (`runner/lib/untrusted.mjs`, `dispatch/untrusted`, and memory's twin) runs one shared vector file.
- **Pending decisions and other agent-written text are enveloped in MCP answers.** `list_pending_decisions` and `get_ticket`'s blocking decisions, a claim's review feedback, the test contract in `get_ticket`, a spec's title, brief and clauses, scope node names and crew's context packet now come back inside `<untrusted-*>` envelopes. REST and CLI answers are unchanged.
- **A `?token=` link no longer replaces the dashboard's stored sign-in.** With a different token stored, the dashboard keeps it, scrubs the link and asks "This link carries a different sign-in. Switch to it?" (Keep current is the default).
- **The release pins what it ships, and the write token never meets repository code.** The image and the delivery sandbox install the Claude Code CLI at a pinned version (`ARG CLAUDE_CODE_VERSION`) on base images pinned by digest, `docker-context-check` fails on an unpinned Dockerfile line, and Dependabot watches the Dockerfiles. The release workflow builds and tests with a read-only token and hands the assets to a separate publish job that holds the write permissions and runs no test or script of the repository on its runner (the image build there still runs the Dockerfile's install and build steps, inside BuildKit, which never sees the token).

### Changed

- Critical-risk changes are never automatic, at either gate. Enabling an autonomy policy at critical is refused ("Not allowed: a person always decides critical changes."), a row that already exists is ignored (a person decides, whatever the row or the mode's floor says, `autonomous` included), and no suggestion is made there. High-risk suggestions now need the repository's own evidence: the cross-repo prior counts at low and medium only.
- `wg ticket tester-pass --as human` without a principal's token no longer records a waiver: use `GAFFER_PRINCIPAL_TOKEN=<token> gaffer wg ticket tester-pass <n>` (see Security). `tester-pass` and `tester-fail` record a principal's verdict as the principal without `--as`; their `--as` now defaults to the runner's `agent` only when no principal is set.
- A dollar cap is now a ceiling for the calls already running. Under any cap, an admitted paid launch books a `reservation` row in the usage ledger before it starts, for its worst case (`GAFFER_MAX_CALL_USD` where set, else `GAFFER_KILL_ESTIMATE_USD`, else $0.05), and admission counts open reservations as spend against the daily and lifetime caps: while other calls are in flight a new call starts only if its own worst case fits beside them. The call's own row names the reservation it settles (`settles`); a launch refused before anything ran releases its reservation; one whose call died without booking keeps holding until the tick's crash path books its kill estimate or `usage-ledger.mjs --reconcile` settles it (`--open-reservations` lists them). A reservation carries no cost, so no cost view counts it as spend or as a call; the run summary shows open ones on their own line. See "Budget admission and reservations" in `docs/CONFIG.md`.
- The eval judge's grade on the Review page is collapsed behind *Show the judge's view*, and opening it before you decide is recorded on the ticket (`POST /tickets/:id/judge-revealed`, `wg review judge-view`). Until it is opened the grade is hidden from the ticket page, the ticket's API reads and `wg ticket show` too, so a reviewer cannot read it there and still count as blind. `wg judge-agreement` takes its figures and reading from blind decisions only and reports the revealed ones apart with the count of each; Health's eval judge line says which is which. Decisions made before the upgrade, when the grade was shown openly, count as revealed.
- A matched experiment's acceptance difference uses Newcombe's paired score interval and reports the discordant tickets, since acceptance is a paired yes or no; ten tied tickets no longer read as an interval of [0, 0]. `wg routing recommend` proposes from an experiment only with at least one discordant ticket and an interval lower bound within a 0.10 non-inferiority margin, and says which condition failed otherwise.
- The non-inferiority margin a matched experiment is judged at is an explicit choice: `gaffer eval experiment --margin` and `wg routing recommend --margin` take it (0 < m < 0.5, 0.10 by default), `results.json` and `report.md` record it, every recommendation prints the margin it used, and an experiment read at a tighter margin keeps it. [docs/eval-harness.md](docs/eval-harness.md) says how to pick one for your work.
- Dispatch's 3,100-line review gate (`reviewGateService.ts`) is now a thin facade over one module per concern under `services/reviewGate/` (approval, staleness and pins, CI, landing, send-backs, the tester lane, tester verdicts); no behaviour, message or API changes.
- `docs/CONFIG.md` is down from 270 rows to 119 an operator could set, one table per area of `runner/config`: a knob read where it is used sits in its area's table, deprecated names have their own table, and names that are not settings (paths the runner derives, plumbing it sets for a child, the packages' and the sandbox image's own variables, test seams) are named once at the end instead of as rows. They still work as before. Four runner file paths the config set for itself are now internal (`_GAFFER_ESTIMATE_LIB`, `_GAFFER_WORKER_MJS`, `_GAFFER_USAGE_PAUSE_MJS`, `_GAFFER_USAGE_WORKER_MJS`), which also keeps them out of the agent's environment; so are the agent id files and the eval ledger (`GAFFER_AGENT_ID_FILE`, `GAFFER_REVIEWER_ID_FILE` and `GAFFER_EVAL_LEDGER` are ignored with a warning, the files stay under `$GAFFER_DATA`).
- The dashboard's single 30,000-line `app.js` is now a small entry that imports one ES module per view and a set of shared modules under `js/`, served from the same origin under the same CSP; nothing on screen changes.
- `settings.json` no longer sets an internal name (any key starting with `_`, such as the module paths the runner runs or its warn-once marks) or a test seam whose value is a command or a module (`GAFFER_WG_LIST_CMD`, `GAFFER_WG_SHOW_CMD`, `GAFFER_WG_DELIVERIES_CMD`, `GAFFER_REDACTION_MODULE`, `DISPATCH_TESTER_VERDICT_CMD`, `DISPATCH_LANE_VERDICT_CMD`, `DISPATCH_ACCEPTANCE_EVIDENCE_CMD`): the file lives where an agent's sandbox may reach, so it must not pick code the runner executes. Each is skipped with a `gaffer: ignoring ... from settings.json` line; the environment still sets the seams.

- The preformatted spend in a paused delivery's Team sheet row (`"$0.9500 spent so far"` in `GET /api/human-queue`'s `reason`): the row now carries `spend_usd`, a number in US dollars (null when the runner relayed none), for the client to format. The string stays in the reason for one release.

A zero, negative or malformed cap, in the knob or an old name, refuses the run (docker would read it as no cap).

### Fixed

- **The autonomy ladder's controls are locked for viewers who cannot use them.** The ladder loads after the page's permission pass, so its lift form and "Sign this row" (created after its own read) stayed enabled for read-only and non-admin viewers, and the client refused the click before any request. Each is now locked when it is created, with the same title and class as the rest of the page; "Review and sign" is locked where its read is refused too (a scoped token).
- **An agent's approval no longer races past an approve step-down.** The autonomy checks ran before the approval read its Git metadata, outside the write transaction, so a step-down (or the approve policy turned off) committed by another connection in that window still let the agent's approval commit and return ready_for_merge; only the landing check refused it later. Both approval transactions (straight to ready_for_merge, and to the tester) now decide the hold and the agent allow-path again inside the transaction, before the ticket moves.
- **A person reopening a delivery a person approved no longer steps autonomy down.** The reopen was written before the landed delivery was classified, so the reopen's new review path (with no approval on it yet) read as an automatic landing: a merge step-down at the ticket's risk and every higher one, explained as "landed automatically". The delivery is now classified from its history as it stood before the reopen, in the same transaction, and the merge classification always reads the path the delivery landed on. An agent's approval that landed still steps down on a reopen, and a landed delivery with no approval on record still counts as automatic.
- **A legitimate checkpoint update no longer refuses a valid principal or signed autonomy row.** A verification read the event-log anchor first and the chain checkpoint later, so one ordinary commit between the two (the anchor and the checkpoint both moved on) showed a checkpoint "past the anchored head" and refused a genuine sign-in, and the refusal stayed cached on the handle until another connection committed. The checkpoint is now read before the anchor and both are pinned before the read snapshot opens, and a cached refusal is reused only while the anchor and checkpoint it was computed from are unchanged. A forged, rolled-back or past-the-anchor checkpoint is still refused.

- **A dispatch call that takes longer than a second no longer fails the tick's helper server.** The wait for a served call's reply polled once a second and read the status of the wrong statement, so the first poll that timed out was taken for a closed reply: the call failed with `WG_SERVER_FAILED` after one second whatever the 120 second budget said, although the command may already have run. The wait now lasts the budget, and a slow answer is an answer.
- **The sandbox-exec profile denies the helper-server pipes by name.** `wg-serve/` was documented as a host-owned directory but missing from the last deny block, so a write root configured to contain `$GAFFER_DATA` re-granted it. The per-tick key was still required to run a request; the directory is now denied like `locks/` and `run-state/`.
- **Dashboard figures.** Two periods with the same rate read "no change" instead of "+0 pts better" or "+0 pts worse" (the two were compared at different precision). Cycle-time percentiles are served in full like the median, so one short ticket no longer shows a p75 below its median. A reason code, status or view name spelled like an object method (`constructor`, `toString`) is an unknown key like any other: the Team sheet threw on such a reason code.
- **The "change moved" notice on Review survives a live refresh.** After an approval is refused because the branch moved, the notice above the new diff stays until that change is signed off; a live refresh arriving while the refused view was loading used to leave only a toast.
- The browser test worlds and the screenshot script keep their factory signing key beside the world (`$OUT/config`) instead of in the operator's `~/.config/gaffer/keys`. Each run added a key there, and a re-run in the same output folder met the previous run's tamper anchor and held its first merge as `unsigned_approval`, which failed the golden path for no fault in the change under test. The golden path now fails if a run writes a key into the operator's home.
- **Runner correctness.** The abandoned-branch sweep no longer deletes unmerged work by ticket number alone: it touches only a branch this factory's ledger says it cut for that exact ticket, never one kept for rework or a pause, and it moves the branch to `refs/gaffer/abandoned/` (logged) instead of deleting it, so a reset factory, a second data dir or an undone Won't do loses nothing. A paid call interrupted outside the delivery lane (a review, a clarify, a judge, any Node launcher) no longer holds its budget reservation for good: the next launch on the same host settles it with a labelled kill estimate once its launcher is provably gone (never one booked from another pid namespace that shares the hostname, such as a container on the host network), and the refusal text no longer promises that a dead call will book its cost. Two review lanes, or two DoD reruns, can no longer take the same lock at once: a dead holder's review claim, DoD rerun lock or poll lock is taken over only through the guarded reap, and a claim whose holder has not written its pid yet is left alone. A cap-hit pause that dispatch refuses is retried, and if it still fails the ticket is parked to blocked (`pause_failed`, branch kept) and the tick reports an error instead of `paused` with the ticket left claimed; a tick killed while the pause is being recorded parks it the same way instead of handing it back to ready. A landing whose mark-merged fails (Poll and `gaffer merge`) is reported as held, not merged, before the digest step and the branch deletion; the next pass marks it done from the recorded landing. The delivery rows and branch name are recorded before the submit, so a tick killed right after it (for example by the outer bound while the eval judge runs) leaves a delivery a person can approve instead of one every policy pack refuses. An approved ticket the runner held for a person (merge gate or CI red) and then unblocked back into the queue counts an attempt and resets its acceptance criteria, as a review rejection does, instead of being redelivered on the previous delivery's evidence, whether it is unblocked from the CLI or with the dashboard's Unblock. A tick whose rework attempt is refused by the budget after a paid first attempt reports an error, not `no_work`, so its day slot is no longer refunded. `MAX_TICKS_PER_DAY` now counts per UTC day, the same day as the dollar cap, instead of the host's local date; the count taken before an upgrade still counts on the day of the upgrade. The budget admission sums spend in integer micro-dollars, so ten $0.10 calls stop at a $1.00 cap instead of admitting an eleventh.
- A credential scoped to some tickets no longer reads a decision shared with a ticket outside its scope through a nested response. It was refused on the decision itself and left out of the list, yet its title and question came back in the ticket's detail (`blocking_decisions`) and its claimability, and `wg ticket show` under `GAFFER_PRINCIPAL_TOKEN` showed it whole. One rule now decides every surface a principal reads: a decision is readable only when every ticket it is linked to is. One that is not still shows where it blocks your ticket, as `{ id: null, title: null, outside_scope: true }` (the dashboard says "A decision outside this token's scope"), and it still blocks; an answered one is left out. The shared token, an unscoped principal and a principal scoped to every linked ticket see the whole decision as before. A factory agent still reads every decision on the ticket it was started for, answers included, whatever other ticket the decision is also linked to; its `list_pending_decisions` now leaves out decisions that are only on other tickets, except for a factory agent started for no ticket (product owner, planning), which still lists every pending decision.
- A request's identity is resolved once. The API looked a principal token up several times per request, so a principal revoked by another process part way through could be taken for the shared operator: its scope check skipped, or a principal minted with its token. Now the first lookup is the request's identity for its whole life, the operator is only whoever presented the shared token, and a principal token that does not resolve is refused (401).
- A feature in the memory ledger is marked shipped only when all of its work has landed, not when its first ticket merges. The feature-planning loop puts the same `Feature-Id:` line on every ticket of a feature epic, and the merge used to ship the feature on whichever of them landed first (external review 17). On every landing the merge now asks Dispatch for the feature's tickets (`wg epic feature-status <id> | --ticket <n>`: every ticket carrying the marker, plus every confirmed member of their epics and each epic's own acceptance ticket) and ships only when every one of them is done; a cancelled (won't-do) ticket is listed but not waited for, and a feature whose every ticket was cancelled is never shipped. The same rule covers a prepared digest delta that names a feature, the PR-mode and merge-lane landings, and `gaffer merge` on a ticket that already landed. When Dispatch or memory cannot be read the landing ships nothing (fail closed, logged), and an idle tick re-evaluates every `building` feature (`merge-ticket.mjs --reconcile-features`), so a feature whose last ticket landed while memory was unreachable is not stranded; it asks Dispatch about every building feature in one call (`wg epic feature-status --batch <id...>`), not one process per feature. A `Feature-Id:` line is text any ticket description can carry (an ingested issue body can quote one), so marked tickets that no feature epic holds never complete a feature, a landing ships only a feature the ledger has in `building` (never a backlog feature or an unknown id), and the planning loop drops any marker line from the planner's ticket text before adding its own. A landing whose epic names two features ships neither and logs why; the idle pass evaluates each by id. A feature waiting on a `failed` ticket stays `building` until that ticket is retried and lands or is cancelled, and `gaffer status` now says so: its "features held" section names each building feature whose other work has landed but which is held by a failed or blocked ticket, a stray ticket carrying its `Feature-Id:`, or an epic that names two features, with the ticket numbers and what to do (`hold` in `wg epic feature-status`). The per-ticket digest update still runs on every merge.
- Feature transitions in the memory ledger are atomic: `advance_feature` / `release_feature` read and validate the current status inside the write transaction (taken with `BEGIN IMMEDIATE`) and update only from that status, so two factories can no longer both claim one feature, and a stale claim or release can no longer move a shipped feature back to `building` or `backlog`; the loser gets the same `illegal_transition` refusal a sequential caller gets. The same read-then-write race is closed in the sibling writers: the feature re-add (`add_feature`), the first digest write and the CLI's partial `digest set` / `digest touch`, lore update / verify / reject / delete / supersede (a reject could hard-delete a record approved a moment earlier), and boundary reject and agent re-declare (which could drop, or rewrite and demote, an edge a human approved meanwhile). `memory features --all --json` lists the ledger across repos.
- One agent review per delivered commit; the tester runs before the reviewer in agent mode too. A delivery goes to the independent tester right after its gates in every review mode (`wg ticket tester-route` now names a `code` per route), the reviewer agent runs only once the tester has nothing left to say about the head (its lane does not gate the ticket, or a PASS covers the head) with the tester's outcome in its packet, a tester FAIL goes to rework with no review paid, and a head dispatch already holds an agent review verdict for is not reviewed again on a later run (before, each daemon pass reviewed the same commit again: 22 reviews on 12 deliveries in one live run). The review pass re-reads the ticket right before it launches the reviewer and does not review one that left review, and a ticket merged or sent back during a review is reported as having left review, never as "reviewer modified the candidate". A rework that resubmits the commit the reviewer agent already asked changes on is not reviewed again and not left in review unannounced: where the runner may act on the verdict it sends the ticket back to rework on it (the retry cap parks a ticket that keeps doing so), otherwise a note on the ticket says that commit waits for a person.
- A trust lock left behind (`~/.claude.json.gaffer-trust.lock`, empty, from a run that is gone) no longer blocks every workspace trust write: the lock records its holder's pid and start identity, and a lock whose holder is gone, that records no holder, or that is older than `GAFFER_TRUST_LOCK_STALE_MS` (default 60 s) is taken over (two takers cannot both win), with one log line. A lock held by a live process is still waited on and then refused. An unparseable `~/.claude.json` no longer leaves the lock behind either.
- No agent runs with its project permissions ignored: when the workspace trust write is skipped, `trust-workspace.mjs` exits 3 and the delivery, bootstrap and clarify launches refuse with `trust_unwritable`, the cause and the fix (a delivery or bootstrap ends the tick as a setup error and releases the ticket to ready), and the review pass holds the ticket for a human. The independent tester and the merge-conflict resolver now trust their own worktrees too (they ran untrusted before, so they could not run the repo's scripts or commit) and refuse to start when that write is skipped. Before, the agent ran untrusted and could not read its ticket, run the tests or commit, the untested scaffold was auto-committed, and an equally blind reviewer sent it back.
- Runner tests run with a private `HOME` (holding a copy of your `.gitconfig`), so no test can rewrite your `~/.claude.json` or leave its trust lock there; `runner/test/run.sh` fails a strict run on a trust lock left in your real `HOME` and lists trust entries added to your `~/.claude.json` during the run.
- Two tester runs for one ticket no longer share, and destroy, one workspace: a second run finds the first one's per-ticket lock and starts nothing (`phase: busy`), and a lock left by a run that is gone is taken over (also when its pid now names another process: the lock records its run's start time). A tester verdict now names the testing round its run started in (`wg ticket tester-pass|tester-fail --round`, `round` on `POST /tickets/:id/tester`), and dispatch refuses one from an earlier round (a rework started a new one) with `STALE_VERDICT`, keeping it as stale evidence: an old FAIL no longer sends a reworked ticket back, and an old PASS no longer sends it on.
- Two paid launches started at the same moment can no longer both pass the dollar cap on the same headroom: reading the spend and booking the reservation run under one lock beside the usage ledger, for the shell seam (`worker_deliver`) and the Node seam (`Worker.deliver`, and the spec author's direct spawn) alike. Before, two launches against a $1 cap both saw $0 spent, both ran, and $1.40 was recorded (external review 16). The safety hook refuses an agent's attempt to settle a reservation (`budget-admission.mjs release`, a `usage-ledger.mjs` row booked with `--settles`), as it already refused `--reconcile`: only the runner settles one.
- A call whose cost was never established (no reported total, no estimate) now holds a lifetime budget (`GAFFER_BUDGET_USD`) until the operator books it with `usage-ledger.mjs --reconcile`, not only until the UTC day turns; a daily cap alone still clears with the day.
- The judge agreement reading no longer says a judge that does not separate accepted from rejected work "is not paying for itself": it reports what it measured (the grade adds nothing the decisions do not show) and says the cost question needs reviewer time and escaped defects measured with and without it.
- The Settings page's load no longer waits for the agent isolation probe in full (up to 15 s on a host whose docker CLI is slow to answer): it waits at most 1.5 s, answers with the posture it has or "still probing", and the finished probe shows on the next load. Concurrent loads share one probe.
- Two workers of a pool reaching their first tick together on a fresh data dir both register the factory agent and the reviewer principal; the one that lost the database lock no longer ends the pool as a setup error. Registration retries up to three times a second apart and names the attempt that succeeded; a refusal that persists still stops the tick and the abort quotes what `wg` said.
- The independent tester's lane, timing and per-criterion evidence read the same in the dashboard and the runner, and its verdict cell says *Not this commit* after a push.
- An epic's acceptance ticket tracks the epic's current scope, counts each member once, and no longer rejects itself.
- A merge interrupted before its tester replay record was written recovers on retry.
- A Poll pressed while the previous one was finishing no longer skips a ticket, and two waiters taking over a dead lock no longer both hold it.
- `gaffer run` delivers again (it had been running dry); `--dry-run` previews each ready ticket once and leaves no trace; a one-shot run no longer sleeps out a usage-window pause; Ctrl-C on `--daemon` finishes the current pass.
- A logged-out agent CLI no longer spends attempts or parks good tickets.
- The scheduler no longer starves a low-priority prerequisite, and an approved but unmerged ticket no longer reads as all clear.
- A parked delivery keeps its branch, an emptied `node_modules` is primed again, and a delivery on a host with no git identity is no longer parked as empty.
- Tick budgets hold under a worker pool, and a dollar cap of 0 or one that is not a number says so.
- A failed database read no longer deletes uncommitted work, and the orphan sweep removes a worktree only when its ticket has ended.
- Processes opening a fresh database together no longer fail with "database is locked".
- A re-added feature no longer loses its ledger data.
- Recording a merge is an admin act on REST as on the CLI; a principal assigns a real reviewer and cannot speak as an agent.
- A PR landing, a CI result and a landing record are accepted only for the ticket's own commits, and two Merge clicks start one merge.
- Onboarding refuses a folder that is not a git repository, the filesystem root and your home directory; re-onboarding no longer files a duplicate intake decision; two repositories with the same name are told apart by path.
- A ticket title or criterion text is one line, contradictory flags are refused, and every REST body is parsed with invalid UTF-8 and bodies over 1 MB refused as JSON errors.
- The event stream no longer goes silent on a cursor past the end, and the dashboard server stops on SIGTERM with a stream open.
- Settings refuses a dollar cap that is not a number and marks the field, and saving Settings no longer turns autonomy off.
- The review packet's attempts N/M shows the retry cap saved in Settings, the one the next send back enforces, instead of the cap the dashboard started with.
- Poll for work says when the runner refused it, run details show "unknown" cost as unknown, and "Delivered today" counts landings.
- The agent inside the docker sandbox can use git and reach its API on a Linux host, and the MCP bridge socket fits macOS's path limit.
- Agent installs work behind a TLS-intercepting proxy, and a repo with no origin is "nothing to push".
- A call that exits non-zero but reports what it spent is booked at that reported cost (never below the kill estimate) for every worker, so a failed $5 call can no longer pass a $1 daily cap as a $0.05 estimate.
- A call that finishes but reports no dollar total no longer counts as $0 against the caps: it is booked at the same labelled conservative estimate as a killed call, with its tokens kept. A call whose cost cannot be estimated at all leaves a row of unknown cost, and with a cap set the next paid launch that day is refused until you book the cost with `node runner/lib/usage-ledger.mjs --reconcile --usd <amount>`. The run summary counts measured, estimated and unknown calls apart.
- The eval judge's grade on the Review page is recorded as seen before it is shown. The review packet no longer carries the grade while the view is closed; opening it is one request that records the reveal and returns the grade, and a failed request shows a plain error with no grade and lets you try again. Before, the page drew the grade first and sent the record afterwards with its errors swallowed and no retry, so a reviewer who saw the grade could be counted blind. `wg review judge-view` takes the same path and prints no grade when the reveal cannot be recorded.
- `usage-ledger.mjs --reconcile` refuses `--usd 0` (it books a positive figure or nothing), a reconcile row at $0 clears no unknown-cost refusal, the safety hook denies the reconcile verb to an agent however the path is spelled, and the usage report shows a reconcile booking on its own line instead of as an estimated call. A failed merge resolver whose envelope reports no dollar total is booked at the kill estimate, and `GAFFER_KILL_ESTIMATE_USD=0` no longer makes a command worker's missing cost count as $0 (only `GAFFER_WORKER_COMMAND_COST_USD=0` does).
- `wg judge-agreement` no longer shows the grade of a ticket in review whose judge's view is closed: it counts it as pending and leaves its pair and verdict out until the view is opened, so a reviewer cannot read the grade there and still be counted blind.
- A pull request merged upstream on a default branch with a slash in its name (`release/v1`) is now recognised as landed while the local default branch is stale.
- A merge that died after a repository's PR merged upstream (or its default branch moved) and before Dispatch recorded it no longer leaves the ticket stuck: the retry finds the approved commit already in the landing target (the remote default for a repo with a PR, the local default otherwise), records the landing, never merges that repo or asks for its PR again, regenerates the tester replay record on what landed and lands the rest. The remote default counts only when the retry's fetch just updated it (a failed fetch takes no shortcut), and the tester and CI rules still apply to that record. Before, the retry refused for good once the provider had deleted the merged branch (`no-head`), or asked the provider to merge the merged PR again.
- The merge lane and the review pass's landing now take the same per-ticket merge lock as `gaffer merge` and the dashboard's Merge now, so a lane retry beside a `gaffer merge` of the same partly landed ticket no longer asks the provider to merge the same PR twice: the second finds the lock held and does nothing.
- A model call whose usage-ledger append fails no longer vanishes from the budget: the append is retried, then the row is held in `$GAFFER_DATA/usage-ledger.held.jsonl`, budget admission counts it as an unknown cost (paid launches under a cap are refused, after a restart too), and `node runner/lib/usage-ledger.mjs --reconcile --usd <amount>` moves it into the ledger once the ledger can be written, exactly once: the reconcile claims the hold file before it moves the rows (a call held while it runs is not retired with them) and skips a held row the ledger already has (a reconcile that died part way does not book it twice). The reconcile moves and books under the budget admission lock, so two reconciles at once cannot book a held row twice, and `usage-ledger.mjs --open-reservations` lists the held rows after the open reservations.
- The docs follow the code, and the docs are indexed in [docs/README.md](docs/README.md).
- Issue ingest no longer drops an issue whose URL is a prefix of an existing ticket's source: a ticket for `.../issues/10` made `.../issues/1` read as already ingested, and Jira `PROJ-1` against `PROJ-10` the same. A ticket's source is the last `Source:` line of its description, compared exactly after the URL is canonicalised (scheme and host case, a trailing slash and a fragment do not make a new issue), so a `Source: https://...` line quoted inside an issue body is not its identity. Dispatch repeats the check inside the transaction that creates the draft, so two ingests racing on one database create one ticket. Tickets written by earlier ingests keep deduping. The idle loops' finding keys are matched the same way, so `loop:web` no longer matches an open ticket for `loop:web-app`.
- A failed webhook or Slack notification no longer writes its URL into the log or the `dispatch notify test` report: Slack keeps the webhook secret in the URL path, which the old message kept (`webhook POST to https://hooks.slack.com/services/T.../B.../<secret> returned 503`). A failure now names the sink, the URL's origin and the status or error code only, for a non-2xx answer, a transport error that quotes the URL, a timeout and an invalid URL, and the notifier scrubs every URL in any sink's error down to its origin. The dashboard link a notification carries loses any user information and query (a `GAFFER_DASHBOARD_URL` set to the `?token=` login link no longer posts the token).
- A notification that times out now aborts its HTTP request instead of leaving it open behind the timeout.
- Text from outside the factory can no longer plant a ticket marker: a `Source:`, `Finding-Key:` or `Feature-Id:` line in an ingested issue body or its labels, in an idle scan's summary of repository text, or in a planned feature ticket's text is quoted as `> ` (still readable), so it no longer dedupes another issue, suppresses an idle loop's draft, or makes the merge ship a feature the ticket does not belong to. Tickets ingested before this keep whatever lines their bodies carried.
- A webhook or Slack notification no longer follows a redirect: a 3xx answer is reported as a failed delivery (sink, origin and status), so a redirect cannot send the POST and its body to a host the notify URL policy would refuse.
- `crew doctor` no longer reports an audit log path as writable when it cannot be written: a path that is a directory, or one whose nearest existing parent is a regular file, now warns.
- Onboarding through the API stops its search for a `.git` folder at `GIT_CEILING_DIRECTORIES`, as git and `dispatch repo add` already do.

## [0.1.0] - 2026-06-17

### Added

Initial public release of Gaffer — a local-first, supervised software factory.

**Dispatch** (`packages/dispatch`) — the control plane. Manages tickets, epics, scopes, and per-repo access. Exposes a REST API, an MCP server, a web dashboard, and a CLI. Enforces the server-side review/merge gate: by default, an agent actor cannot approve or merge its own work.

**Crew** (`packages/crew`) — the factory runtime. An MCP tool server that exposes factory-level tools to agents, plus a hooks engine and idle loops for drafting work, ingesting issues, and repo onboarding.

**Memory** (`packages/memory`) — durable, human-gated knowledge. A knowledge base (lore) plus the Repo Understanding engine: Repo Digest, feature ledger, and grounded lore drafts. Seeded at onboarding; refreshed as tickets merge. Also usable standalone as `memory-mcp`.

**Runner** (`runner/`) — the bash orchestrator. Spawns a `claude -p` agent per ticket with a 66-skill library. Includes a deterministic PreToolUse safety hook (`safety-hook.mjs`) that scopes writes to the per-ticket git worktree and fails closed. Model tiering: planning on a strong model, implementation on a fast one. Per-call resource caps (wall-clock timeout + agent turn cap).

**Web dashboard** — seven views: Overview, Work, Review, Epics, Map, Memory, Settings. Review is the human gate where tickets wait for approval before any merge occurs.

**Safety boundary** — worktree isolation (every ticket in a throwaway git worktree), deterministic regex-based safety hook, server-side human review gate. Autonomy flags (`DISPATCH_ALLOW_AGENT_APPROVE`, `MERGE_ON_AGENT_REVIEW`, `MEMORY_AUTO_APPROVE`) are opt-in and off by default.
