# Security model

Gaffer runs **shell-capable autonomous agents** on your machine, against your repos, with your API keys. That is powerful and inherently risky. This document is honest about both what protects you and where the limits are — read it before pointing Gaffer at anything you don't fully trust.

## Threat model in one line

You are trusting an LLM agent with a shell. The agent's *inputs* (ticket text, repo contents, ingested issues) may be attacker-influenced; the agent itself may be prompt-injected. Gaffer's job is to **contain what the agent can do** and **keep a human in the loop on anything that ships**.

## What protects you (defense in depth)

- **Deterministic PreToolUse safety hook** (`runner/safety-hook.mjs`): scopes all writes to the active worktree (`GAFFER_WRITE_ROOTS`), denies reads of secret files by *path* (not a reader-binary denylist), denies the control-plane CLI and raw DB access to the agent — including a **self-spawned control-plane MCP** (`node …/dispatch/dist/mcp`), `node -e` reaching the dist or the DB, and reading another process's environment (`ps`, `/proc/*/environ`) to lift a token — blocks force-push / branch ref rewrites of the base branch (`git branch -f`, `update-ref`, …) / history-execution git config / scheduled-execution primitives, and resolves wrapped/assignment-prefixed commands so `env tee`, `VAR=1 mv`, `sh -c '…'` can't smuggle a verb past it. It **fails closed**: when it can't prove a target is in-scope, it blocks. Every hook entry in the settings template carries `"onFailure": "block"` and an explicit 60-second `timeout`, because Claude Code's default for a hook that times out or crashes is to run the tool anyway; the settings writers refuse a template without them, and `runner/test/safety-hook-redos.test.mjs` pins that repeated wrapper options (`nice -n nice …`, `env -u env …`) cannot drive the deny rules into exponential backtracking.
  - **Input-size cap**: before any rule or regex runs, the hook measures the raw stdin payload (before it is even parsed) and then every field it inspects (the tool name and `tool_input`'s `command`, `file_path`/`filePath`/`notebook_path`, `path`, `pattern` and `glob`). A payload over **2 MiB** (the cap that bounds the fields no rule reads, such as a Write's `content`, so a 1 MiB Write is still decided by its path), or a single inspected field, or those fields together, over **64 KiB** (65,536 bytes, UTF-8), is **blocked** (exit 2) as `unverifiable: tool input too large (… bytes > …-byte cap)` and logged to the safety-blocks ledger as `oversized-input`: an input too large to analyse quickly fails closed instead of being decided by super-linear regexes (a ~100 KB deep path took 60–70 s; it now blocks in milliseconds). The caps sit well above real use (the largest Bash heredoc in 14,578 recorded agent calls was ~30 KB) and are constants (`MAX_INSPECTED_FIELD_BYTES`, `MAX_PAYLOAD_BYTES` in `runner/safety-hook-core.mjs`), deliberately not configurable by environment. Under the cap, adversarial shapes can still be slow; the 60-second hook timeout with `onFailure: block` is what bounds those.
- **Throwaway git worktrees**: each ticket runs in a disposable worktree; the real checkout is never touched. Teardown runs on the explicit success/error paths **and** from an `EXIT`/`INT`/`TERM` trap, so a crash or signal mid-delivery cannot orphan a worktree or a half-finished `gaffer/ticket-*` branch — the trap is guarded so a legitimately-delivered branch is preserved for review/merge. Teardown removes only what the run still owns (`runner/lib/cleanup-ownership.sh`): right before each worktree removal and branch deletion it checks Dispatch that the ticket's newest claim is still this run's, and it never deletes the branch of a ticket that is a submitted review candidate. A worker whose lease expired or that was stopped therefore cannot delete the branch its replacement submitted; it logs that the resources belong to another attempt. An unreadable Dispatch keeps everything.
- **The runner's own git never runs repository code** (external review #9): every git command the runner runs on the host for bookkeeping (the auto-commit, worktree add/remove, fetch, merge, push, status, the landing in `lib/land.sh` and `bin/merge-ticket.mjs`, and the node helpers they spawn) carries `core.hooksPath=/dev/null` and `core.fsmonitor=false` through git's environment channel (`GIT_CONFIG_COUNT`, `runner/lib/git-safe.sh`, exported by `factory.config.sh`), and every code-running key of the ticket's repositories that points into the checkout or comes from a file inside it (filter, diff and merge drivers, textconv, `core.sshCommand`, `core.askPass`, credential helpers, `gpg.program`, pager, editor, trailer commands, `remote.*.uploadpack`, git-lfs custom transfers) is overridden with an inert value (`runner/lib/git-safe.mjs`). A driver neutralised this way fails closed: a merge driver that cannot run is a conflict and holds the landing. The safety hook refuses agent edits to hook scripts (`.husky/`, `.githooks/`, anything under the repository's `core.hooksPath`), hook-manager configs (lefthook, pre-commit, overcommit), repository git config files (`.gitconfig`, `*.gitconfig`, `.lfsconfig`, any file `include.path` names) and a `.gitattributes` line that assigns a filter, diff or merge driver, and `git config` / `git -c` of any of those keys, each with a reason that says a person changes them (`runner/test/git-hooks-host.test.sh` drives a real tick with a tracked hook the agent rewrote; `runner/test/safety-hook.test.mjs`).
- **Server-side human review gate**: the merge gate is enforced in the control plane, not by convention. **By default** an `agent`-type actor cannot approve a review or grant itself repo access, and — whatever the autonomy flags say — an agent actor whose id matches the agent on the ticket's most recent claim is refused (**reviewer ≠ author**, checked in the control plane; the runner's review pass presents a distinct `<agent>/reviewer` principal); in factory context the agent-facing MCP tools additionally refuse to **submit or claim** a ticket even with an explicit token (submission is runner-owned), so a disobedient agent cannot self-submit a no-op delivery past the DoD gates. Its other ticket-scoped writes (acceptance criteria and their runner-executed `check_command`, dependencies, the test contract, the testing-lane flag, per-repo delivery, ticket-linked decisions) are bound to the ticket the runner mounted that server for (`GAFFER_CLAIM_TOKEN` / `GAFFER_SCOPE_TICKET` / `GAFFER_REVIEW_TICKET`) or to drafts the same server created, and an agent can turn the independent tester on but never off. The "done" gate verifies the **real `git diff`** — not an agent-authored evidence string. Every approval — the runner's agent review and a human's — **names the commit it reviewed, per write repository**: the Review view sends the head commit the diff endpoint rendered, the CLI takes `--commit <repo>=<sha>`, and the control plane **refuses** the approval (`409`, `stale_revision`) when any branch head differs from what was shown, so an approval can never cover a commit pushed between the render and the click. The approval and its per-repo **pins of the reviewed commit** (system evidence rows an agent cannot forge) are written in one transaction, and every landing path merges only those commits, holding a branch that moved after the approval. An approval **covers every write repository** on the ticket: while any write repo's delivery head cannot be resolved (no checkout here, an unreadable path, a missing delivery branch) the control plane refuses it (`409`, `repo_unavailable`) for humans and agents alike, so no approval pins a subset; a write repo left unpinned by an older approval keeps the ticket out of *done* and no landing path lands its head. A multi-repo ticket is **done only when every pinned commit has landed** (a system landing record per repo, or the commit verifiably on the default branch); the landing record is the merge lane's to write: the safety hook denies `wg ticket record-landing` (and `wg ticket ci-result`, the required-CI record) to an agent shell like `mark-merged`, and the control plane refuses a local landing whose commit git does not show on the default branch, and a PR landing without a PR on record for that repository or whose change the default branch (or its remote-tracking copy) does not carry; a partial landing stays in *Ready for merge*, visible as "Partly merged" (a red merge gate holds it for a human instead), and can only be finished: it cannot be cancelled, and a send-back to rework holds it for a human rather than re-queueing it; a conflict resolution the resolver agent commits is **re-gated** (no conflict markers, the repo's DoD gates green on a clean checkout of the committed resolution, so nothing the resolver left uncommitted can make it pass) before it can be re-reviewed, and is moved off the branch if it fails. Nothing lands on the strength of each side's own gates: every landing path — **each repository** of a multi-repo ticket included — first builds the merge of the approved commit onto the **current** target in a scratch worktree, runs the repo's DoD gates on that merge, and lands exactly the gated merge commit **only while the target is still the gated head** (compare-and-land; a moved target is re-gated) — a red combination is held for a human (`merge_gate_red`) with the target untouched. With CI required, the CI result is recorded **for the candidate commit** and approval, a tester PASS and the landing decision all require a recorded PASS for it; a red result for an approved ticket holds it (`ci_red`). An agent-supplied `pr_url` is treated as an evidence/navigation link **only**; it never substitutes for the server-recomputed `git diff`, so a bogus URL cannot satisfy the gate. The opt-in autonomy flags (`DISPATCH_ALLOW_AGENT_APPROVE`, `MERGE_ON_AGENT_REVIEW`, `MEMORY_AUTO_APPROVE`) deliberately relax this — they are **off by default**, and enabling one removes the corresponding human gate. Treat them as a conscious trust decision, not a convenience toggle.
- **Enforced Definition of Done (I3)**: before a delivery may rest in the human review lane, the **runner** (never the agent, which would be trusting the fox to count the hens) runs the enabled DoD gates — **tests / typecheck / lint** — deterministically in the delivery worktree, each bounded by `gaffer_timeout`. A failing gate **auto-rejects the delivery back to rework** with the gate name + a captured output tail recorded as evidence; a human never spends time on a delivery that doesn't pass its own gates. This turns review from "read all the code and hope" into "audit a pre-verified delivery." It is toggled only by env (`GAFFER_DOD_TESTS` / `GAFFER_DOD_TYPECHECK` / `GAFFER_DOD_LINT`, default on; see `docs/CONFIG.md`): crew.yaml's `definition_of_done` block is not read by the runner, and `crew doctor` warns when it is changed; the typecheck gate runs the repo's package.json typecheck script (auto-detected from the **base** branch, so a delivery cannot delete the gate away; `GAFFER_DOD_TYPECHECK_CMD` overrides it); a gate with **no configured or detected command is skipped, not failed** (and logged); `GAFFER_DOD=0` disables enforcement (the pre-I3 behaviour). **Shipped gates:** tests · typecheck · lint · **machine-checkable acceptance criteria** (an AC's `check_command`, executed by the runner in the worktree **byte for byte as stored** — no trimming, no TAB/newline rewriting — and dispatch refuses a result whose command differs from the stored one; the done gate refuses a checked AC the runner has not passed, so agent-written evidence cannot substitute for the check) · the **merge gate** (the same gates on the merge of the approved commit onto the current target, before it lands). **Deferred (documented follow-ups, not yet gates):** coverage-did-not-decrease (needs a stored baseline), SAST/SCA (needs I2), docs-updated. (CI-green is the opt-in H3 gate, `GAFFER_REQUIRE_CI`, which controls approval when on.) The gate is a *quality* barrier, not a security boundary — the human review gate above remains the thing that actually keeps a human in the loop on anything that ships. The Review view's verdict strip shows these gate results and each checked criterion's exit code only from rows recorded by the `system` actor (an agent's look-alike row is ignored), and the tester's verdict only from the row the tester pass/fail path recorded (named by its `ticket.tester_passed`/`ticket.tester_failed` event), and flags an agent-claimed whole-suite test count (from the current attempt) that the runner's recorded count contradicts. That count is what the test runner printed while running the delivered code, so a delivery can still print a false one: it is a consistency check for the reviewer, not a gate. What it prints cannot pass for a gate result, though: the kept summary lines have tabs turned into spaces and lose any line that starts with `GATE` or `---`, and gate rows are read only outside the framed output blocks.
- **Gate integrity: the gate resists an agent that weakens its own tests.** A gate that only asks "do the tests pass?" can be passed by deleting the failing test, renaming it out of the runner's glob, marking it `.skip`, or rewriting the `test` script. The runner now resists each of these. (0) **The base is a recorded commit, not a branch name:** when the runner cuts the delivery branch (`worktree add -B`) it captures the commit the branch was cut at, at that moment, before any agent runs, and records it (`ticket_repo_delivery.base_sha`); a kept or resumed branch, and every in-tick retry that builds on the previous attempt's branch, keeps that commit — a retry never re-reads the branch tip, which by then holds the agent's own commits. The stored base is write-once: dispatch refuses a different one (`STATE_CONFLICT`) unless the runner says it cut the branch again from the base (`--base-recut`, refused for an agent like `--base-sha`). The gate, the integrity row and dispatch's server-side scan all read from that commit. A base branch name can be moved from inside the worktree (`git branch -f main HEAD`, `git update-ref`), which would hide every commit before the move; the safety hook also denies those ref rewrites for any non-`gaffer/` branch, in the spellings git accepts (combined flags such as `-fq`, a flag after the arguments, global options such as `-c k=v` / `-C dir` before the subcommand, `--`, abbreviated long options, `checkout -B`, `switch -C`, a `symbolic-ref` write, `push`/`fetch` into a local path), allowing a force only when every argument is a `gaffer/…` branch or a `HEAD` start point; and dispatch flags the scan incomplete when the base branch no longer contains the recorded commit. Deliveries recorded before this column fall back to the merge-base of the base branch name. (1) **Commands are read from the base commit:** when a gate command is a package-manager script call (`npm test`, `pnpm run lint`, `yarn typecheck`, …), the script comes from the base commit; when the delivery changed or removed it, **added or changed one of its `pre`/`post` hooks**, or changed a script it reaches through a simple chain (`test: npm run unit`), the **base expansion runs instead** (`base-pinned`; the delivery's hooks never run), so editing `package.json` cannot redirect the gate. Each gate row records where its command came from (`registered` / `base` / `base-pinned` / `head` / `unresolved`) in the evidence. (2) **An `integrity` row** compares base with the delivery worktree (committed and uncommitted) and FLAGs deleted or renamed test files, added skip/focus markers (`.skip`/`.only`/`.todo`/`xit`/`fit`, also behind a modifier such as `it.concurrent.skip`, node:test's `{ skip: true }` / `{ todo: … }` options, the runtime `t.skip()` / `this.skip()` / `ctx.skip()`, and code after a comment on the same line such as `/**/ test.skip(…)`, bracket access such as `test["skip"](…)`, a `.skip(` chained on its own line, `const { skip } = test`, `@pytest.mark.skip`/`xfail` and module-level `pytestmark = pytest.mark.skip`, `unittest.skip`, `raise SkipTest`, `pytest.importorskip`, `__test__ = False`, `t.Skip`, a Go `//go:build ignore` constraint, `#[ignore]`, `@Disabled`/`@Ignore`, RSpec `xit`/`pending`, `markTestSkipped`, `@tag :skip`), any change, removal or **addition** among the scripts the gate scripts reach (`test`, `lint`, `typecheck`, … and any script a gate command names; their `pre`/`post` hooks; and the scripts their bodies run through `npm|pnpm|yarn|bun run X`, `pnpm X`, `run-s`/`run-p`/`npm-run-all` words and `npm:X`), a modified or deleted test-runner config (vitest/jest/playwright/pytest.ini/conftest.py/…, and the `jest`/`mocha`/`ava`/`c8`/`nyc`/`tap` keys of a package.json), one the delivery **added** once the base already has tests (a greenfield scaffold with no tests yet is not flagged; a git-ignored one on disk counts too), and a package-manager rc file (`.npmrc`, `.yarnrc`, `.yarnrc.yml`, `bunfig.toml`, at the root or in any package directory) the delivery **added**, modified, deleted or renamed — such a file reconfigures how `npm test` runs (`script-shell=/bin/true`, `node-options=--test-name-pattern=…`) without touching `package.json` or a test, so it is flagged on add too, and the runner also checks the worktree on disk so a git-ignored `.npmrc` that never reaches a commit is flagged as well; dispatch holds an agent approve on the runner's integrity FLAG in the latest DoD checklist it recorded (rows an agent recorded are ignored), not only on its own diff scan, so a FLAG the committed diff cannot show still holds. Test files follow each stack's default discovery (for Python, unittest's `test*.py` — Django's `app/tests.py` — as well as pytest's `test_*.py` / `*_test.py`). It also FLAGs a test file that **lost test cases** — the definitions (`it(`/`test(`/`describe(`, `def test_`, `func Test…`, `#[test]`, `@Test`, `[Fact]`, RSpec `it`, PHPUnit `function test…`, ExUnit `test "…"`) the diff removed outnumber the ones it added, counted per language family so tests moved to another file never count, and a commented-out test counts as removed — and a test file whose **assertions fall to zero** while it still holds tests (`expect(`/`assert`/`should`/`t.Error…`/`assert_eq!`/`Assert.…`/`$this->assert…`), naming the file and the counts (`test cases removed: 3 → 0 in test/a.test.js`); a new file has nothing to fall from. A scan that cannot see the whole change FLAGs too — including a test file replaced by a symlink or another file type, and a tracked file git has been told not to compare with the working tree (`git update-index --skip-worktree` / `--assume-unchanged`, a sparse checkout): the gate runs what is on disk while `git diff` and the auto-commit see the index copy, so such a file is named and FLAGged. The scan reads hunks with `--text` and fixed `a/` `b/` prefixes (a `.gitattributes` `-diff`/`binary` or diff-prefix config cannot hide added lines) and switches off `core.fsmonitor` / `core.ignoreStat`. (3) **Dispatch recomputes the same check server-side** from the real `git diff` against the recorded base commit (risk kind `test-modified`, high); an unallowed `test-modified` is a **hard hold** on the auto-ship path: an agent approve is held for a human whatever the ticket's declared risk (`ticket.autoship_escalated` records the hold). A human's approve is never held. (4) **Only a human may excuse it:** `allow_test_changes` (`wg ticket allow-test-changes <n>`, `POST /tickets/:id/allow-test-changes`, or Allow test changes on the Review page) turns the integrity FLAG and the hold into PASS with a note and drops the annotation to medium; dispatch refuses agent and system actors, the safety hook denies the CLI verb, no MCP tool exposes it (likewise an agent can never change a repo's registered DoD commands: `repo set-commands` is denied by the hook and refused for an agent actor server-side), and every change is a `ticket.test_changes_allowed` event. The allowance does **not** change what the gate runs: a gate script the delivery changed still runs as the base commit has it, so a ticket that legitimately changes `scripts.test` can still fail its tests gate and go back to rework; to change the gate itself, a human changes the repo's registered test/lint command, or the script change is merged to the base branch first. **Limits of this first slice:** it FLAGs, it never FAILs a delivery; a weakened assertion inside a test that still runs (`expect(x).toBe(x)`, or assertions removed while at least one remains in the file), tests replaced by trivial ones in another file of the same language (moves are netted per language so they never flag), and a test that never ran on base are not detected; a test-runner config added while the base has no tests yet is not flagged (a greenfield scaffold adds every config), nor is pytest configuration inside `pyproject.toml` / `setup.cfg`; package-manager settings outside the four rc files (pnpm settings in `pnpm-workspace.yaml`, a user-level `~/.npmrc`, `npm_config_*` environment variables) are not checked by the scan — the agent's environment is an allowlist and the safety hook denies the plain writes to an `.npmrc`, but the scan does not read `pnpm-workspace.yaml` settings; a bootstrap (greenfield) delivery that adds an rc file is held for a human like any other; a compound gate command (`npm test && npm run lint`) runs as registered, and a changed script reached only through a compound script body (`run-s unit e2e`) still runs as the delivery has it (the evidence note names it and the integrity row FLAGs it); the base commit is only as good as its record: a delivery recorded before the column, or one whose record failed to write (fail-soft) and whose branch is resumed on a later tick, falls back to the merge-base of the base branch name; the hook rule against ref rewrites reads the command's tokens but is defence in depth, not a jail (a script file the hook never sees can still run git; the recorded base commit, not the hook, is what keeps the scan honest); the review diff itself (and the other observed-risk annotations) is still computed against the base branch's merge-base; the landing paths (`bin/dod-regate.sh`: the merge gate on every landing path, and the conflict-resolution re-gate) read the gate scripts from the gated target head (the default branch's tip for a resolution) and add an integrity row comparing it with the gated tree — FLAG only, so a landing is never refused for it (a merge gate PASS records no evidence, so the flag there is the gate output and the stderr log; the resolution re-gate's checklist goes on the ticket for re-review, and dispatch recomputes `test-modified` on the resolved branch).
- **Prompt-injection handling**: the untrusted free-text ticket fields the agent reads through `get_ticket` — **title, description, acceptance-criterion text, and review feedback** — plus the title, question and human answer of each resolved ticket-linked decision (`resolved_decisions`) — are wrapped server-side in `<untrusted-*>` quarantine envelopes carrying a standing "this is data, not instructions" notice; the runner prompts and skills carry the same framing, and event/comment payloads are redacted out of the agent's context entirely rather than enveloped. The live agent's environment is built from an **allowlist** (`env -i` + only what `claude` and its MCP tools need): every ambient credential **environment variable** is stripped — `GITHUB_TOKEN`, `AWS_*` access keys / secret / session token, `DISPATCH_API_TOKEN`, and any `*_TOKEN` / `*_SECRET` / `*_KEY` / `*_PASSWORD` (except `ANTHROPIC_API_KEY`, which `claude` needs for auth). This applies to **both** the shell `claude -p` launches (delivery, bootstrap, agent-review, clarify) and the `.mjs` runners (decompose, product-owner, onboard). The scrub does **not** remove file-, keychain- or socket-based credentials: the agent keeps the operator's `HOME`, so a CLI logged in on the host (`gh`, `aws`, `gcloud`, `docker`, `npm`, …) would authenticate as the operator. The hook covers that residual instead — the CLI credential stores (`~/.config/gh/`, `~/.docker/config.json`, `~/.kube/`, `~/.config/gcloud/`, `~/.azure/`, `~/.pypirc`, `~/.pgpass`, `credentials.tfrc.json`, `~/.claude.json`, plus `.ssh/`, `.aws/`, `.netrc`, `.npmrc`, `.git-credentials`) are secret paths on every read vector, and the credential-using commands are refused in command position: `gh`, `aws`/`gcloud`/`az`/`vault`, `kubectl`/`helm`/`terraform` against real state (offline forms such as `kubectl kustomize`, `helm template` and `terraform fmt|validate` stay allowed), container `login`/`context`/`-H`/`DOCKER_HOST`, host namespaces, `--privileged` and bind mounts whose source is outside the worktree, git credential helpers and global git config writes, registry publish/login/token commands, and macOS `security` keychain reads. That is regex defence in depth, not a jail: on a host that holds real cloud or registry logins, run with `STRICT_MODE` on the docker provider (it does not mount the host `HOME`) or as a dedicated user.
- **Independent acceptance is checked on what lands**: an epic is reported as accepted only when the runner's landing path recorded that the independent tester's assertions passed on the exact revision that landed: the merge gate replays the tester's test files (from `gaffer-tests/ticket-<n>`, never its agent wiring) on the merge candidate (the registered test command itself, its env assignments, config, markers, build tags and features kept, with only the tester's files and a proof reporter appended; a command that cannot be extended safely runs as registered) and holds a failure (`tester_replay_red`) with the default branch untouched; each file must show the runner's own evidence that it ran there (reporter events, a JSON report, node ids, `go test -json` events), and a file without it holds the landing too (`tester_replay_unverified`), so the record lists only assertions that ran. The tester's PASS binds the test identities the runner's own clean replay saw pass in the tester's files (recorded by the runner as `system`; dispatch refuses them from an agent, a person or an admin, and the safety hook refuses `tester-pass` in every spelling), and the landing replay requires every one to execute and pass: a skipped, todo, missing or renamed one holds, a failed one is red, and dispatch refuses a replay record that does not prove all of them, so no path turns that hold into a green. An older PASS without identities is file-level evidence only (a file counts as run when any of its tests ran) and is shown as such. What the replay proves is the execution of those named tests under the registered command on the candidate; it does not prove what the tests assert. The tester lane's clean replay, where the identities are measured, runs the tester's files unsandboxed as the runner user: its signing key reaches only the reporter, but a test there can read the runner's environment and files and call the dispatch CLI as the system actor, so the identities are evidence against a non-adversarial tester's tests, not against tester code attacking the replay (sandboxing that replay is a follow-up). The evidence is made hard to forge from the code under test: node:test events are signed by the reporter with a per-replay key that is never written to a file and is removed from the environment test processes inherit (it stays readable to same-user code as the runner's initial environment, and a registered command whose runner is not node:test hands it to that runner's processes, so the signature stops printed look-alikes, not code written to forge it), where the run is still by path a reported file set must match the files run, a JSON report must have the runner's shape and a consistent count, `go test -json` wraps anything a test prints, and printed text never counts. It is not proof against a deliberate attack on the replay itself (a same-user process reading the runner's environment, a node loader module the registered command imports, a test that rewrites a JSON report in process); the delivered code is reviewed. The record (`gaffer-tester-replayed:<sha>`, a system evidence row) is written by `wg ticket record-tester-replay`, which the service accepts from the `system` actor only (not an agent, a human or an admin) and the safety hook refuses to agents; a replay-shaped row an agent records through the MCP is not counted.
- **Resource caps**: per-tick wall-clock timeouts, agent turn caps, and dependency installs forced to `--ignore-scripts` (no `postinstall` code execution) and run inside the validation sandbox with a stripped environment (a package manager can still run repository code such as a `.pnpmfile.cjs`).
- **Tamper-evident event log**: every `work_events` row is chained by a SHA-256 hash (`prev_hash`, `hash`), so a row rewritten, deleted or re-ordered after it was written breaks every hash after it; `dispatch events verify`, `dispatch doctor` and the Health view re-derive the chain and name the first altered row. The chain has **no key**: it catches accidental and naive edits, but anyone with write access to the SQLite file can recompute every hash after an edit — to detect that, record the chain head that `dispatch events verify` and `dispatch doctor` print somewhere the DB's writers cannot reach, and compare it later. Opening the DB never re-chains a row whose hash was blanked (only a pre-v23 log, on upgrade, is backfilled); `dispatch events rechain --confirm` is the explicit repair and records itself in the log. It does not authenticate who wrote a row either (see the actor-identity limit under residual limits). Each event also carries the runner tick that wrote it (`correlation_id`), so one tick's runner and agent writes read as one trail.
- **CI gates on the factory's own code**: the dependency audit gate (fails on any HIGH/CRITICAL advisory not justified in `.github/audit-allowlist.txt`), shellcheck over the ~27k lines of production bash, **CodeQL** (JavaScript/TypeScript, security-and-quality queries), **gitleaks** over the full history, the red-team docker containment gate, a browser regression of the dashboard (Playwright + axe), and the generated `docs/CONFIG.md` drift check. Every action is pinned by commit.
- **Optional OS sandbox** (`runner/lib/sandbox.sh`): a kernel-level containment layer via a provider seam. The **`docker` provider** (`SANDBOX_PROVIDER=docker`, experimental) runs the agent in a container with **read isolation** (mounts only the worktree, `$GAFFER_DATA`, the factory's `runner/`, `packages/` and `node_modules/`, and the dependency links the runner itself created — host `$HOME`/creds/other repos are absent) and **egress isolation** (an `--internal` network with an allowlist proxy for the model endpoint + registries); the macOS **`sandbox-exec`** provider is a *write-only* boundary (no read or network isolation); a microVM is future. `GAFFER_STRICT_REQUIRE=1` makes it **fail closed** — when no OS sandbox provider is available (e.g. `sandbox-exec` on a non-macOS host, or no Docker daemon), the runner refuses to launch rather than silently degrading. **Enabling any autonomy flag auto-defaults `STRICT_MODE=1` and `GAFFER_STRICT_REQUIRE=1`** (see below), so unattended runs fail closed without an OS sandbox unless you explicitly opt out. The wrap is applied inside the single worker seam (`runner/lib/worker.sh`), so **every** agent spawn — delivery, bootstrap, reviewer, clarify, eval judge — is contained the same way. **Mounts are an allow-list of runner-created paths, never chosen by the repository**: everything under a write root is writable by the repository and by the code it runs, so a worktree `node_modules` symlink is bind-mounted only when it resolves exactly to the primary checkout's own `node_modules` at the same relative path (the shape `gaffer_link_node_modules` makes, the primary found through git's two-way worktree registration). A link to `$HOME`, `/etc` or another repository, a symlink chain, a relative `..` escape, or a `node_modules` symlink committed in the primary itself is skipped with a `WARNING` naming the path, never mounted; a forged worktree `.git` file, or a `.git` symlink to another worktree's, gets no git metadata mounts, **and no host path under the repository's `.git` is writable from the container** (external review #9): the container gets a private git dir at the worktree's gitdir path (its own HEAD, a snapshot of the refs, a hook-free config, new objects written privately, the host's objects reached read-only through an alternate), and after the container exits the wrapper imports only the worktree's own branch with a compare-and-swap `update-ref`, so a `git update-ref refs/heads/main` run by a test inside never reaches the operator's branch and the validation profile imports nothing (`runner/test/sandbox-docker-git-isolation.test.sh`, live in the containment gate), and a `.claude/skills` symlink in a write root is never followed: it is neither mounted nor, in the legacy layout, left unmasked, even when it names `$GAFFER_DATA/skills-mounts/<key>` (the runner installs skills as real copies inside the worktree and creates no such link) (`runner/test/sandbox-docker-mounts.test.sh`, live in the Docker containment gate). **The factory's own tests never delete outside their temp dir**: every runner test checks its `mktemp` result before using it (a failure exits 70 with "refusing to run") and removes its temp dir only through `gaffer_test_rm_work` (`runner/test/lib/tmpdir.sh`), which refuses an empty path, `.`, `/`, `$HOME`, the directory the test started in, the repository root, an ancestor of any of them, or anything outside a temp root; `runner/test/no-unchecked-mktemp.test.sh` holds the rule for every future test and `runner/test/mktemp-failure-safe.test.sh` proves a forced `mktemp` failure leaves the checkout and its `.git` intact.
- **Landing never overwrites an ignored local file** (external review #9): every merge or checkout that updates the operator's checkout (`bin/merge-ticket.mjs` and `lib/land.sh` compare-and-land, the PR fast-forward, `lib/automerge.sh`) passes `--no-overwrite-ignore`, and before the landing is recorded both paths check by name for a file the branch adds where the operator has an ignored copy; either refusal holds the ticket for a human (`ignored_file_in_the_way`) with the file named and the copy untouched (`runner/test/land-ignored-file.test.sh`).
- **Required CI fails closed** (external review #9): with `GAFFER_REQUIRE_CI` and PR creation on, the runner records the requirement on the ticket before it submits the delivery for review (`wg ticket ci-required`, a `ticket.ci_required` event), and dispatch reads CI as required from that mark as well as from recorded results. Approval, a tester PASS and the landing check then need a recorded PASS for the exact commit under review: nothing reported is a hold ("CI required: not reported", `held_ci`, POLICY_DENIED with `reason: ci_required`), a PASS for another commit of the ticket is a hold, and an unresolvable candidate is a hold. A gate that cannot read CI (no `gh`, no GitHub remote) no longer returns success: under the strict policy the delivery goes back to rework, and under `GAFFER_CI_TIMEOUT_POLICY=proceed` it reaches review with approval still held (`packages/dispatch/test/ci-required-before-review.test.ts`, `runner/test/h3-ci-gate.test.sh`).
- **Onboarding reads stay inside the repository, and remote URLs lose their credentials** (external review #9): every file onboarding, the repo scan, the digest and the file-card refresh read (README, manifests, the Makefile, ADR folders, changed sources) is resolved to its real path and refused when that lands outside the repository root, symlinks included (`runner/lib/repo-boundary.mjs`, `packages/crew/src/safety/repoBoundary.ts`); the prompt and the repo digest name each refused file and why. Userinfo is stripped from https-style remote URLs at the source (crew's git adapter, the onboarding scan, the prompt facts, the repo canonical) and from every onboarding log line, so `https://user:token@host/x` reaches prompts, digests, lore, events and logs as `https://host/x`; ssh and scp-like forms are left as they are (`runner/test/onboard-boundary.test.sh` greps the prompts, the onboard log, the events and the databases; `packages/crew/test/repo-boundary.test.ts`).
- **Planning agents run read-only.** The propose/analyse agents read untrusted input (a brief, an onboarded repo), so a prompt injection there must not be able to write anything. Where they run:
  - `decompose` and `spec-author` run in a **throwaway agent home**, `<GAFFER_DATA>/<decompose|spec-author>-XXXXXX` (falling back to the OS temp dir), removed after the turn. It holds a role-scoped `.claude/skills` mount and the rendered safety-hook settings — PreToolUse matchers for Bash, Write/Edit/MultiEdit/NotebookEdit, Read and Grep/Glob/LS, plus the recursive secret-file Read deny rules — which are parsed and verified before the spawn (a missing or unwired template refuses the run). `GAFFER_WRITE_ROOTS` is the home. Whether Claude Code loads project hooks in that directory is not pinned by a test, so nothing relies on it.
  - `onboard-analyze` still runs in the factory's own source dir (`RUNNER_DIR`) with **no project settings**, so it is hook-less. The template's secret-file Read deny rules are passed to it through `--disallowedTools`, so Claude Code still excludes nested `.env`, key and token files from its Read/Grep/Glob. Its per-file card and card-review turns run text-only instead: no built-in tools (`--tools ""`), an empty MCP config under `--strict-mcp-config`, from an empty scratch cwd that is also their only write root and holds only the verified safety-hook settings.

  All three are launched with the **complete write/exec tool set denied** — `--disallowedTools Write Edit MultiEdit NotebookEdit Bash` — leaving only Read/Grep/Glob plus the MCP tools they connect via `--mcp-config`. **Design decision (kept):** a *denylist* of write tools, **not** an `--allowedTools Read Grep Glob` allowlist — because these agents connect MCP, and an allowlist would sever those tools (or require enumerating every MCP tool name). The residual: a *new* write tool added to Claude Code must be added to the denylist. That is covered by a periodic audit of Claude Code's write/exec tool set (and the agent-spawn tests pin the current denied list); if Claude Code ever exposes a stable `--allowedTools` MCP-wildcard, revisit the allowlist as the more robust form.
- **The model scout runs read-only, and only when you turn it on** (`GAFFER_SCOUT=auto|on`, off by default; `runner/lib/scout.sh`). It reads the ticket text, which is untrusted, so it gets the same posture as the planning agents and less: one call through the worker seam (budget admission as kind `scout`, the OS sandbox wrap when on, the agent-env scrub), from an empty scratch cwd that is its only write root and holds the verified safety-hook settings, the real repo as its only read root, built-in tools limited to `--tools Read,Grep,Glob` with Bash, Edit, Write, MultiEdit, NotebookEdit, WebFetch, WebSearch, Task, Agent and TodoWrite also denied by name, an empty MCP config under `--strict-mcp-config`, `--disable-slash-commands`, and a turn cap (`GAFFER_SCOUT_MAX_TURNS`, 6). It runs only on the claude-code worker: the command worker contract cannot limit the tools to those three, so under it the model scout is skipped. A call that was spawned is booked in the usage ledger even when it was killed with no envelope. Its reply is data: a path is kept only when it exists at the base commit, a symbol only when its file contains it, every list is capped, and what is kept reaches the delivery prompt inside the `<untrusted-scout>` envelope labelled as a model's reading. The deterministic scout spawns nothing. Its risk record (`wg ticket scout-record`) is the runner's: the hook denies the verb to agent shells, and dispatch refuses any actor but system or admin and recomputes the level from the ticket's own declared risk, so a record can only raise it.

## Honest residual limits (the ceiling)

- **The safety hook is a regex/string analyzer on bash.** It is hardened and fails closed, but a string bouncer fundamentally cannot win against a determined agent that constructs paths dynamically, decodes arguments at runtime, or writes via a child process's syscalls. The deny list is now matched against the command as the shell would resolve it as well as against the raw text: quotes and backslashes stripped from every word, the variables a command assigns substituted into its later `$NAME` uses, no-op wrappers and `xargs` peeled off, the bodies of `eval`, `sh -c`, `$(…)` and inline `node -e` / `python3 -c` / `perl -e` / `ruby -e` programs scanned as commands of their own, and the privileged CLIs reached by file path mapped to their names; a program name the hook cannot see (built by `$(…)` or an unassigned variable) in front of a control-plane verb, a privileged CLI fed its verb by `xargs` from stdin, and a decoded payload piped into a shell are refused outright. The words that name what a privileged CLI does (the noun and verb for `wg`, `dispatch`, `fg` and `crew`, the verb for `gaffer` and `memory`, after its root options such as `--db`) must be plain literals on the command line: a `$(…)`, backticks, a variable the command does not assign, a glob or a brace expansion in one of them is refused (`wg ticket tester-r$(printf o)ute 5`, `wg ticket $v 5` after `read v`), and so is a CLI that `xargs`, `parallel` or `find -exec` runs with one of those words missing or filled from their input (`echo approve | xargs wg ticket`, `xargs -I{} wg ticket {} 5`, the same inside `sh -c`), `fd -x` or a `parallel -I` replace string. The same holds behind a subshell or group, a `case` pattern, a function the command defines, `exec -a`, `coproc`, `pnpm wg` / `yarn wg`, and programs that run their arguments as a command (`watch`, `strace`, `taskset`, `script -c`, `ssh`, `watchexec` and the like), and a privileged CLI nested deeper than the hook reads is refused outright. Words after the verb are not judged this way, so `wg ticket show $T` and `cat ids | xargs -n1 wg ticket show` still run, and so does `wg help $X` (help prints, it acts on nothing). `wg import $FILE` is refused: import is an operator's act. What stays out of reach is unchanged in kind: a compiled binary, a script the agent writes and then runs, and content-only data flows. The deterministic boundary shrinks the residual to dynamic *reads* and fully-dynamic non-secret *paths*; it does not eliminate it.
- **The `sandbox-exec` (Seatbelt) profile still permits writes under `$GAFFER_DATA`.** The profile re-grants writes to the worktree, `$GAFFER_DATA` (the MCP SQLite dbs, agent id/log, the MCP runtime and the profile itself live there), the temp dirs and the std streams — and the worktree itself sits under `$GAFFER_DATA/worktrees/`. So at the OS level an agent process can write `$GAFFER_DATA/settings.json` (which `factory.config.sh` applies as env defaults: any runner knob, e.g. `GAFFER_DOD=0` or `GAFFER_TESTER_REPLAY=0`), `usage-pause.json` and the `*.jsonl` ledgers. **The safety hook is the control there:** it refuses every write vector to those paths that `runner/test/safety-hook.test.mjs` pins — the Write/Edit/MultiEdit tools, shell redirects and `tee`, `cp`/`mv`/`install`, `sed -i`, inline `node`/`python`/`perl`/`ruby` writes (paren-less forms included; a path built at runtime fails closed), and `git -C`/`--work-tree`/`--git-dir` into the data dir — whether the path is absolute, reached through `..` from the worktree or through a symlink inside it. A child process's own syscalls (a compiled binary, a script file the agent writes and runs) are invisible to the hook, so this is the regex ceiling above, not a jail. Narrowing the profile to the dbs and runtime files is the real fix; it is not done blind because it needs a macOS run to verify (the MCP servers and the claude process must still start). This is also why the `command` worker provider, which has no hook, refuses `sandbox-exec` outright (item below). The `docker` provider does not expose `settings.json` or `usage-pause.json` to the agent: in bridge mode only the MCP socket, the bridged MCP config (read-only) and the hook's two append-only ledgers come from `$GAFFER_DATA`, and the legacy layout masks every entry off its allowlist.
- **Actor identity is authenticated per principal; a tokenless CLI is operator trust.** The REST surface accepts **named principal credentials** (`dispatch principal create <name>` / `POST /api/principals`, `gfp_…` tokens, SHA-256 stored, shown once) bound to an actor identity (`human` or `admin`), a capability (`full` or `read`) and an optional **scope**: `--repo <name>` / `repos` and `--ticket <n>` / `tickets`. Every event and evidence row written under one names that principal's actor, revocation is a stamped row in the audit trail, only the shared operator token (or the CLI without a principal token) may mint or revoke principals (a principal token gets 403 `PRINCIPAL_ADMIN_REQUIRED`, so a CI credential cannot mint an operator-named admin identity or revoke someone else's), and `GET /api/whoami` reports how a request authenticated and what scope it holds. Recording a merge (`mark-merged`) and sending a done or approved ticket back to review (`reopen-for-review`) are admin acts with one rule on REST and the CLI: the shared operator token (and a tokenless CLI with `--as admin`) acts as admin, a named principal needs actor type `admin` and is recorded under its own id, and a `human` principal is refused (403 `ACTOR_NOT_PERMITTED` on REST, `--as admin` refused on the CLI). A CI bot that records merges is minted with `--admin`. Assigning a ticket's reviewer (`PUT /tickets/:id/reviewer`), a named principal names a registered agent or a live principal, never a made-up id, and a scoped principal names only itself or the reviewer already on the ticket, so it cannot pick who reviews its own work (the CLI, acting as a principal, accepts only `--reviewer <itself>`). The shared `DISPATCH_API_TOKEN` still works and still acts as the single `dispatch-api` operator, so a factory that mints no principals is unchanged.
  - **Scopes.** One evaluation (`packages/dispatch/src/services/accessScope.ts`) decides every scoped request, for REST, the CLI and the factory MCP mount's own ticket scope alike. A ticket is in scope when it is one of the principal's tickets, or when every one of its write repositories (every linked repository, for a ticket with no write repo yet) is in its repo scope. The read rule is the write rule: a scoped principal sees exactly the tickets it may change. The API's authorisation layer (`api/scopeGate.ts`) maps every request a principal sends to an action before any route runs; the ticket list, the board, the batched ticket details, the human queue, claims, decisions and the live event stream are filtered to its tickets (and `/scope/repos?all=1` to the repositories it reaches), a ticket outside them is 403 `SCOPE_DENIED` (details name the scope, the reason and the ticket or repositories outside it), and everything factory-wide (polling, planning, the map, specs, epics, runs, cost, health, the audit tail, settings) is refused. Repository-level writes (registering, linking or hiding a repo, its default branch and DoD commands, onboarding, a ticket's repo access, settings, idle loops, autonomy policy) need an `admin` principal; a scoped admin gets only the repositories in its scope. A scope combines with `read`: scoped reads only. Approvals by a scoped principal are recorded under its own identity. An in-scope ticket does not open the tickets around it: a dependency on a ticket outside the scope is shown by number and status only, and adding or removing one needs that ticket in scope too; every repository a new ticket names counts, read access included (the delivery agent reads a read repo); and a ticket's epic and map membership is the operator's, because joining or leaving an epic rewires its acceptance ticket.
  - **The CLI.** Direct database access is operator trust: whoever can open `dispatch.sqlite` can change anything in it, so a tokenless `wg` records `$USER` and enforces nothing, and `wg whoami` says that identity is asserted, not authenticated. Principals are the way to delegate narrower access: with `GAFFER_PRINCIPAL_TOKEN=<token>` (or `--as-principal <token>`) the CLI resolves the principal from the same table the API uses (an unknown or revoked token does nothing), records writes under its identity, refuses an option that would record another one (`--as system|agent`, `--reviewer <someone else>`) and every command that is runner or agent bookkeeping recorded as the system or an agent (`attach-evidence`, `claim-ticket`, `submit`, `runner-release`, `ticket pause`, `ac check-result` and the like), and enforces its read-only flag and scope through the same evaluation, with every command mapped to an action and an unmapped one treated as a factory-wide write. `gaffer approve` and `gaffer merge` honour the same variable. This narrows what a person or bot holding only a principal token can do; it does not protect the database file itself, so keep the file (and the shared token) with the operator.
  - What remains asserted: the agent's actor id on MCP writes. It is bound to its per-ticket claim token, the runner scrubs the API token from the agent's environment, the safety hook refuses `principal create|revoke` and `--as-principal` in an agent shell, and the review gate refuses an approval from the agent on the ticket's latest claim (reviewer ≠ author).
- **No TLS.** The dashboard and REST API speak plain HTTP. By default they bind loopback (`127.0.0.1`), so the token never leaves the machine. `gaffer dashboard --lan` changes that, and so does publishing the container's port beyond loopback (`GAFFER_PORT=0.0.0.0:8787`): on a LAN the bearer token, the full one included, crosses the network in the clear, and anyone who can see that traffic can approve, merge and start paid runs with it. Use `--lan` only on a network you trust; otherwise reach the dashboard through an SSH tunnel (`ssh -L 8787:127.0.0.1:8787 <host>`) or a reverse proxy that terminates TLS, and give viewers a read-scoped token (`GAFFER_DATA=.gaffer node packages/dispatch/dist/api/bin.js print-read-token` from the checkout, or a principal minted with `--read`) rather than the full one. `print-read-token` derives from the token in `$GAFFER_DATA/dashboard-token`; run it without the factory's `GAFFER_DATA` and it reads (or creates) `~/.gaffer/dashboard-token` instead and prints a token the dashboard won't accept.
- **OS sandbox providers — `docker` is experimental-but-real; a microVM provider is a design sketch, not code.** The **`docker` provider** adds read + egress isolation on any host with a Docker daemon, and its containment is **red-team-gated in CI** (host secret unreadable, egress DNS + raw-IP denied, only the allowlist proxy escapes, all capabilities dropped except `DAC_OVERRIDE`, `no-new-privileges`). A **full delivery through it is proven in CI too, on Linux**: the `sandbox-delivery` job runs one ticket through the real `tick.sh` with `SANDBOX_PROVIDER=docker` on a real daemon on a GitHub Linux runner (a non-root host user, the container as root), with a deterministic stub agent installed as the delivery image's own `claude`. The agent runs inside the container, records its evidence through the MCP bridge (the host-side dispatch server holds the claim token, which never enters the container), commits into its private git dir (the host imports only the ticket branch afterwards; a ref the agent moves inside, such as `main`, never reaches the host); the DoD gates run in their own container under the validation profile; the result envelope is parsed and the ticket reaches review. From inside, the agent checks that no database, `settings.json`, host `HOME` or host canary file is visible and that a write beside the canary is refused, that git trusts its mounts and that its env points at the egress proxy; the runner holds a decoy credential that must reach the agent and must not reach a gate, and the tests gate fails unless it runs in a container with no database, bridge socket, host `HOME`, canary or model credential; no host ref but the ticket branch may move (`runner/test/sandbox-docker-delivery.test.sh`). The honest ceiling now: the stub decides what runs, a real agent does not, and this is the bridge layout of a Linux host: on macOS Docker Desktop the bridge is off and the masked-mount fallback below applies, which no CI job delivers through. The same delivery with the real `claude` is the opt-in `workflow_dispatch` workflow `.github/workflows/sandbox-live.yml`, never run on a push or a pull request, so a live agent inside the container is proven only where someone runs it with their own credential (docs/docker-sandbox-provider.md, "Prove it on your own fork"). The container runs as root with only `DAC_OVERRIDE`, so on a Linux host the files it creates are root-owned; a non-root `--user` is the next hardening step. The macOS **`sandbox-exec`** provider is write-only (Apple-deprecated; no network isolation). So on a non-macOS host **without** Docker the deterministic hook is the only boundary and `strict` reduces to `autonomous`; **with** `SANDBOX_PROVIDER=docker` available, `strict` gets real read+egress containment cross-platform. `GAFFER_STRICT_REQUIRE=1` fails closed if no provider is available rather than silently degrading.
- **Worker provider containment: a second, real worker needs the docker sandbox.** The runner reaches its agent through a provider seam (`GAFFER_WORKER_PROVIDER`) that mirrors the sandbox seam, at both runtimes (`lib/worker.sh` `worker_deliver`, `lib/worker.mjs` `deliver`), and every lane goes through it (the greenfield repo classifier, the one lane that used to spawn `claude` on its own, included), so a command factory makes no `claude` call. Two providers are real. `claude-code` (the default) runs `claude -p`, guarded by the PreToolUse safety hook. `command` runs an operator-supplied program (`GAFFER_WORKER_COMMAND`) under the contract in [docs/worker-providers.md](docs/worker-providers.md): the prompt (in a per-call file, inline too when it is 64 KiB or less), MCP config, model and turn-cap hints arrive as `GAFFER_WORKER_*` variables, the environment starts from `env -i` with the same allowlist scrub minus the `claude-code` auth surface (plus only the names `GAFFER_WORKER_COMMAND_ENV` lists, never the runner's own tokens), and a small JSON envelope comes back on stdout. Any other value (`codex`, `local`, …) still **fails closed**: exit 70, no envelope, no spawn. The load-bearing tension is unchanged: **the safety hook runs in-process inside `claude -p`**, and a command worker has **no equivalent**, so its containment has to come from the OS, and only one OS boundary holds without the hook. The rule, enforced in code at every spawn site: **a command worker launches only inside the `docker` sandbox with the host-side MCP bridge.** `sandbox-exec` is refused (its profile still grants writes under `$GAFFER_DATA`, the limit above, and nothing but the hook refuses a write to `settings.json`, the databases or the ledger), and so is docker without the bridge (the legacy layout mounts the databases read-write), and so is any wrap a caller hands the seam that is not the docker wrapper. `factory.config.sh` defaults `GAFFER_STRICT_REQUIRE=1` and `STRICT_MODE=1` for it, the tick parks the ticket `strict_require_unavailable` before it composes a wrap that would not hold (never counted as a failed attempt), and the seam itself refuses with exit 75 (naming the fix) whatever `GAFFER_STRICT_REQUIRE` says, so a dashboard-launched Node lane can't bypass it either. The one exception is an **explicit** `GAFFER_STRICT_REQUIRE=0` **in the environment**, the operator asserting that the whole runner is contained out-of-band: honoured, and logged as a `WARNING:` when the config loads and at every spawn, exactly like the autonomy flags; a `settings.json` value is ignored under this provider. The provider knobs themselves (`GAFFER_WORKER_PROVIDER`, `GAFFER_WORKER_COMMAND`, `GAFFER_WORKER_COMMAND_ENV`, `GAFFER_WORKER_COMMAND_COST_USD`, `GAFFER_SANDBOX_WORKER_COMMAND`) are environment-only like `GAFFER_ALLOW_UNCAPPED`, so a written `settings.json` can never point every agent turn at another executable. The program must live where no agent can rewrite it: the seam refuses one under `$GAFFER_DATA`, a write root or the call's directory (as written, through a symlink, or resolved), or writable by its group or others. Under docker the wrapper forwards no `claude` credential into a command worker's container, mounts only this call's bridged (token-free) MCP config and prompt file from `$GAFFER_DATA`, and the program's environment is built by `env -i` inside the container. Budget admission, the per-call timeout (the whole process group: TERM then KILL in the shell runner, KILL in the Node launchers) and every gate after the call apply unchanged. The second consequence, one layer down, is handled by a **parser adapter** (`lib/worker.mjs` `normalizeCommandEnvelope`): it reads only the documented fields from the last 16 MiB of stdout and writes the canonical envelope, so the ledger and the cap/spend guards read the command worker through the same `{resultText, usage, capHit, stopReason}` contract. Its honesty rules: **a command worker's reported cost is operator-trusted and the caps count it, at no less than a per-call floor** (`GAFFER_WORKER_COMMAND_COST_USD`, else the call's dollar cap, else `GAFFER_KILL_ESTIMATE_USD`): a cost left out or reported lower is booked at the floor (`cost_basis: "floor"`, the worker's own figure kept as `reported_cost_usd`), so a worker cannot beat the daily cap by reporting $0; only an explicit `GAFFER_WORKER_COMMAND_COST_USD=0` books an unreported cost as `"unknown"` ($0); every row names `worker_provider: "command"`; and a command envelope can **never** read as a usage-window refusal or an authentication failure, the two outcomes that release a ticket without counting an attempt, because the program writing it is not a CLI the runner can trust. What stays weaker than `claude-code`: the turn cap, tool restrictions and per-call dollar cap are hints the runner cannot enforce inside the program, so the docker sandbox, the wall-clock timeout, the between-call caps and the gates are the whole boundary; and a credential named in `GAFFER_WORKER_COMMAND_ENV` is readable by everything the worker runs and rides the host-visible `env` argv, as the `claude-code` key does for `claude -p`. Under the docker provider a timeout kills the `docker run` client, and a container whose process ignores the signal can outlive it until it exits (for both providers; an `--init` or named-container cleanup needs a live Docker run to verify).
- **Network egress isolation depends on the provider.** The `sandbox-exec` provider has **none** — it wraps the whole `claude` process (which needs the network), so an agent that can run code can reach the network (macOS `sandbox-exec` cannot express host-granular egress rules — its network filter is all-or-nothing, and denying it breaks the agent's own model API calls; host-level egress control requires the proxy the `docker` provider supplies). The **`docker` provider does** isolate egress (the container has no route out except the default-deny allowlist proxy). **Extending the allowlist:** the proxy permits the model endpoint + common package registries out of the box; to allow an extra host (a private git host or package registry) *without rebuilding the image*, set `GAFFER_EGRESS_ALLOW="host1,host2"` or list hosts (one per line) in `$GAFFER_DATA/egress-allow.txt` (override the path with `GAFFER_EGRESS_ALLOW_FILE`). Operator entries are treated as literal hostnames — regex-escaped and anchored — so a broad pattern like `.*` **cannot** widen the allowlist to match every host; invalid entries are dropped with a warning, never turned permissive. The proxy restarts automatically when the effective allowlist changes.
- **Idle-loop repo commands are refused on the host under strict containment.** The idle maintenance loops run repo-supplied commands bare on the host in the repo checkout: the coverage lane's `coverage_command` (the repo's own test suite, i.e. code agents wrote), the dependency lane's `audit_command` (e.g. `pnpm outdated`, which loads the repo's `.pnpmfile.cjs`) and the tsc/semgrep oracles. Under `GAFFER_STRICT_REQUIRE=1` crew refuses all three (`coverage_scan_refused` / `dependency_audit_refused` / `oracles_refused` events) unless the operator sets `GAFFER_IDLE_HOST_EXEC=1` to assert out-of-band containment; the in-process scans (greps over the checkout) still run.
- **Validation runs under the agent's OS sandbox — and only that.** The Definition-of-Done gates and the machine-checkable AC commands execute code the agent has just modified (its test files, imports and config) — a `pnpm test` is trusted, the code it loads is not. The runner now hands the gate runner the **same OS wrap** the agent got (`GAFFER_DOD_WRAP`: the `sandbox-exec` profile or the docker wrapper, same write roots), and reads the verdict **outside** that process. The ceiling is the provider's: with no provider active (the default on a Linux host without Docker) the gates run bare with the runner's privileges, exactly as contained as the agent was — so for unattended runs put the **whole runner** in an isolated VM/container with only the intended repos and credentials, not just the agent. `GAFFER_DOD_SANDBOX=0` opts a repo out (a gate that cannot run inside the image), and is logged. **The pre-gate dependency install is part of validation**: a package manager executes repository code even with `--ignore-scripts` (a `.pnpmfile.cjs`, a yarn `yarnPath`), so `gaffer_dod_install_deps` runs through the same wrap with the `validation` profile and a stripped environment (`env -i`: no operator tokens, a throwaway `HOME`, so no `~/.npmrc` auth). Under `GAFFER_STRICT_REQUIRE` an install with no wrap is **refused** (nothing executes; the test gate then reports the missing dependencies), and the host-side primary-checkout prime is skipped, because it runs before any wrap exists.
- **Inside the `docker` provider the data plane is on the host; the container holds no database — on every execution path.** The dispatch and memory MCP servers run on the **host**, spawned per agent run by `runner/lib/mcp-bridge.mjs serve` from the rendered runtime config (its env, including the claim token, stays host-side); the container is handed a *bridged* config whose servers are `mcp-bridge.mjs connect` over **one mounted unix socket**, and `$GAFFER_DATA` is not mounted — no SQLite file, usage ledger, settings, dashboard token or other worker's claim token exists in the worker's filesystem. Both launchers (`lib/worker.sh` and the Node `lib/worker.mjs`) run the same bridge lifecycle. The wrapper (`lib/sandbox-docker.sh`) never *infers* a layout from an absent socket: a spawn that carries an MCP config with the bridge on and no socket is **refused**; a spawn with no MCP servers gets a `none` layout (no databases); the **validation stage** (DoD gates, AC checks) runs under an explicit `validation` profile with no data plane, no bridge and **no model credential**, whatever the agent's bridge did before — so agent-modified tests execute with nothing of the factory's decision state or secrets in reach. The one remaining ceiling is **macOS Docker Desktop**, which cannot bind-mount a host unix socket into its VM: there `GAFFER_MCP_BRIDGE=auto` resolves to off, the wrapper falls back to the masked DB-directory mount with the servers inside and logs a WARNING that the databases are reachable — force `GAFFER_MCP_BRIDGE=1` on a Linux host, or run the runner in a Linux VM. The socket is `0600` and per spawn; the docker containment gate proves the bridge round (databases absent, token absent, MCP round trip), the validation profile (databases and credential absent) and the refusal.
- **Merge provenance trailers are a record, not a proof.** A landed delivery's merge commit carries `Gaffer-Ticket`, `Gaffer-Reviewed-By` and `Gaffer-Gates` trailers read from the dispatch DB (`runner/lib/provenance-trailers.mjs`; values are flattened to one printable line, so an actor id cannot add a trailer). They are unsigned: anyone who can write the repo can write the same lines. `GAFFER_PROVENANCE_TRAILERS=0` turns them off.
- **A live run needs a dollar cap.** `gaffer run`, `loop.sh` and the dashboard's Poll for work refuse to start a live run while neither `GAFFER_DAILY_BUDGET_USD` nor `GAFFER_BUDGET_USD` holds a positive figure (`runner/lib/budget.sh` `gaffer_spend_cap_ok`); a dry run is never refused. Every other paid launch (onboarding analysis, decompose, product owner, spec author, merge resolver, tester, reviewer) is refused the same way at the worker seam (`runner/lib/budget-admission.mjs`). `GAFFER_ALLOW_UNCAPPED=1` is the operator's explicit opt-out and is read from the environment only: the Settings API does not accept it, and both the runner (`runner/factory.config.sh`) and the dashboard process (`applySettingsToEnv`) skip it when they apply `settings.json`, so a hand-edited settings file cannot lift the cap.
- **An agent cannot claim a usage limit to dodge the park.** A delivery refused by the model's usage window is released to ready without counting an attempt and pauses the factory (`lib/worker.mjs` `detectUsageLimit`, `lib/usage-pause.mjs`). Only the CLI can say so: every text pattern, the legacy `Claude AI usage limit reached|<epoch>` form included, matches only on an error envelope (`is_error: true`, an `error_*` subtype or `type: "error"`), and the structural rows read typed fields the CLI sets. On a success envelope `.result` is the agent's own reply, so an agent that prints a limit string goes down the ordinary failure path (no-commit counter, park for a human) and cannot cycle its ticket uncounted or halt the factory.
- **Budget caps are admission-controlled, and the dollar cap fails closed.** The per-run `MAX_TICKS` and per-day `MAX_TICKS_PER_DAY` are enforced by *atomic reservation* (one locked read-modify-write per tick, refunded when the tick provably spent nothing), so a worker pool cannot overshoot them; `GAFFER_DAILY_BUDGET_USD` halts when today's spend **cannot be measured** rather than reading it as $0. The lifetime `GAFFER_BUDGET_USD` is checked the same way before every tick claims or spawns anything (tick, Poll for work, daemon): at $0 headroom no new paid work starts, and a budget whose headroom cannot be computed halts. What remains soft: spend is summed from the usage ledger after each call returns, so a single call that runs long past the cap is bounded by the per-tick timeout and turn cap, not by the dollar figure.
- **The model credential is visible to the worker inside the sandbox.** Whether it's `ANTHROPIC_API_KEY`, a `CLAUDE_CODE_OAUTH_TOKEN`, or a mounted `~/.claude/.credentials.json`, the agent process needs it to authenticate, so code running *inside* the guest can read it — the *runner/orchestrator* never handles the raw value, and the egress allowlist limits where a leaked credential could be sent, but it is **not invisible to the worker**. Treat it as scoped-but-present.
- **Notification sinks are an outbound channel.** The webhook (`GAFFER_NOTIFY_WEBHOOK_URL`) and Slack (`GAFFER_NOTIFY_SLACK_URL`) sinks POST human-gate events to a URL you configure. Because those URLs are also editable from the dashboard, they pass an **SSRF policy**: http(s) only, and no loopback / link-local / private-range destination unless `GAFFER_NOTIFY_ALLOW_PRIVATE=1`; a refused URL is skipped loudly and never builds a sink. Outbound bodies are **redacted by default** — a minimal body (kind · ticket number · status · dashboard URL only), dropping the ticket `title`/`detail` free text a prompt-injected agent can influence, so an untrusted endpoint is not an exfiltration path. Set `GAFFER_NOTIFY_FULL_PAYLOAD=1` to include the full free-text body — only when the endpoint is inside your trust boundary. (The old opt-in-to-redaction `GAFFER_NOTIFY_REDACT` is deprecated; `GAFFER_NOTIFY_REDACT=0` is still honoured as a full-payload request.) Treat the notify URL like any other outbound integration — point it only at endpoints you trust. **The URLs themselves are credentials** (a Slack incoming-webhook URL is posting authority on its own), so the settings API never returns them: `GET /api/settings` reports a secret-bearing key (`secret: true` in `SETTING_DEFS`, which new secret keys inherit) as `configured` plus the URL's `host`, to every principal, env-backed or file-backed; only an **admin** principal (the operator token, or a named principal with actor type `admin` and full capability) reads the value back, through `GET /api/settings/secret/:key`. A read token or a `human` principal gets 403. The dashboard shows a masked field with Replace and Remove.
- **The independent tester runs only where a test command is registered, and its per-criterion notes are its own word.** With `GAFFER_TESTING` unset, the tester gates a testable ticket only when every write repo has a registered test command (Review and Health name the repos where it is off); an epic's acceptance ticket is always tested. Where it gates a ticket it runs before the human review, and the control plane refuses a person's approval of any commit the tester has not passed (`not_tested`), so the commit approved is the commit tested in the repository the tester ran in; on a multi-repo ticket the other write repositories' commits are reviewed, not tested. The route into testing (`wg ticket tester-route`) is the runner's (system or admin) and the safety hook denies it to agents. What the runner proves is that the tester's test files passed the repo's registered test command on a clean checkout of the tested commit (and again on what lands); a tester PASS the runner could not replay that way (no registered test command, `GAFFER_TESTER_REPLAY=0`) is held for a human as unverified on every ticket, and dispatch refuses an automated PASS that does not carry a passed replay (skipped, failed or none). The replay state on the verdict is the runner's report, not something dispatch re-checks: what keeps an agent from forging one is that agents cannot run `wg ticket tester-pass` or `bin/tester-run.mjs` (the safety hook), have no MCP tool that records a verdict, and no named principal can act as an agent. The tester's per-criterion `manual_note`s are claims: nothing checks that a test exercised the criterion's behaviour, and the proof that each file ran is signed only for node:test (other runners fall back to the registered command). A test contract seeded from a ticket's title names the behaviour, not a real endpoint or command.
- **Acceptance profiles prove that registered commands behaved as registered, nothing more.** For a ticket with the `cli` or `api` profile, the runner runs the commands a person registered (`wg ticket acceptance-profile`, the ticket page; human or admin only, refused for agents in the control plane and denied to agent shells by the safety hook, as is `wg ticket acceptance-evidence`, the system-only record of the run) in a fresh checkout of the tested commit of their own, before and apart from the replay of the tester's tests (none of the tester's code has run in it), and dispatch refuses an automated tester PASS that does not name a passed record on that ticket for the same profile, that commit and the current contract hash, whose every case held (`ACCEPTANCE_EVIDENCE_REQUIRED`); a person's PASS is recorded as a waiver. The delivery agent can only raise a unit contract to a profile name; it never supplies the commands, which come from a person only. What is proven: those argv lists exited and printed as expected, the files named exist, and the probes got the statuses, keys and schema shapes named (a JSON-schema subset: type, required, properties, items, enum, local `$ref`). The runner never adds a shell, but an argv a person writes as `["sh", "-c", "..."]` is a shell they chose. What is not proven: that the commands cover the acceptance criteria (a person chose them), anything the expectations do not name, and behaviour under real data or load. The commands run with a stripped environment (PATH, a throwaway HOME, TMPDIR, locale, CI=1 and the spec's own variables; a spec cannot set HOME, TMPDIR, the loader's or shells' startup hooks such as `LD_PRELOAD` or `BASH_ENV`, or `GAFFER_*` / `SANDBOX_*`) under the same OS sandbox posture as the DoD gates (the validation profile, no data plane, no model credential; the spec's variables reach the command inside the wrap, never the wrapper); with no OS sandbox they are as contained as the gates are, and a required sandbox the host cannot supply refuses the run (the PASS is held), even with `GAFFER_DOD_SANDBOX=0`. Each command's process group is killed when it returns, and the api service's group when the probes end, on a timeout and when the runner stops the profile process (a process that starts its own session escapes the group). The checkout's file diff covers the checkout only (not `node_modules`, which is linked from the primary checkout, nor TMPDIR); a probe's body is read up to 1 MB. The api profile binds a local port the kernel picks and is refused under the docker provider; a probe answered while the service had exited fails. Output excerpts are redacted with the crew secret patterns and bounded; a secret in an unrecognised shape can still appear in an excerpt. Like the replay, this is not proof against a deliberate attack from code the runner executes as the same user: the tester's test files run unsandboxed in the replay and could read the runner's files or call the dispatch CLI as the system actor, and a process the tester's session left running could reach the checkout. The record carries a digest of its canonical form and an HMAC of that digest with a key kept in `$GAFFER_DATA/acceptance-signing.key` (mode 0600). Nothing verifies that signature yet: dispatch checks the record's actor, uri, ticket, profile, commit, contract and cases, not the signature, and the landing path does not re-check the record, so today the signature only lets someone holding the key audit a stored record later; anyone who can write the dispatch database as the runner's user can also write a record.
- **The opt-in autonomy flags remove protections by design.** `DISPATCH_ALLOW_AGENT_APPROVE` lets the agent approve, and `AUTO_MERGE` + `MERGE_ON_AGENT_REVIEW` together let that approval land without a human (`AUTO_MERGE` alone only lands what a human approved; `REVIEW_MODE=both` keeps a human confirm on every approval); `MEMORY_AUTO_APPROVE` lets the model-derived memory the runner files (the requirement distilled from a delivered ticket, onboarding induction lore) go live immediately, which re-opens cross-ticket memory poisoning. Lore a delivery agent suggests through its memory MCP server stays a draft even then: the runner pins `MEMORY_AUTO_APPROVE=0` in that server's environment. **A draft is invisible to factory agents in every read path** — `search_lore` (even when asked for drafts), the duplicate feedback `suggest_lore` returns, `get_lore` by id (answered exactly like a missing id, so an id learned elsewhere neither fetches the text nor confirms the record exists) and `report_conflict` — so one agent's unratified suggestion cannot reach another agent's context before a human approves it. Only enable these with **trusted input**.

- **A same-ticket teardown can still meet a fresh delivery in a narrow window.** When an attempt that lost its claim tears down (its worktree and, for an empty delivery, its branch), every destructive step first checks that the run still owns the ticket's resources, and two Polls never overlap (the poll lock). What is left is check-then-act: a pool worker or another runner can claim the same ticket, run its gates and cut a fresh worktree at the same path, or a branch whose tip equals the base, between the old attempt's ownership check and its `git worktree remove` or `update-ref -d`. That needs the old attempt descheduled for the new one's whole claim-to-worktree path (seconds of Dispatch and git calls) inside a window of a few hundred milliseconds (the worktree) or microseconds (the branch). The new delivery then loses its worktree or branch and that attempt fails; nothing already approved or landed is touched. Closing it needs one per-ticket lock held in the tick's own shell across both sides, which the portable lock (`gaffer_with_lock`, a subshell on the flock path) cannot be.

## Running it safely

- Keep the human review gate **on** for anything that matters.
- Do **not** point Gaffer at untrusted issues/repos (or enable the autonomy flags) without a real sandbox provider and a machine whose blast radius you accept.
- **Revocation and landing, unattended.** A cancellation (`wg review reject --to cancelled`) or a red required check recorded while a merge gate runs stops every landing that has not started: each landing path re-checks the ticket, its approval and required CI in one Dispatch transaction immediately before a default branch moves or a PR merge is requested, per repository, and lands nothing (`not landed: <reason>`, non-zero exit) once revoked. A landing that had already started is not undone; the revocation reports it (`landed_already`, a warning naming each repository and commit) so you can revert by hand (won't do and a board move report it too); the started landing is still recorded and the merge exits 4 with `LANDED AFTER A REVOCATION`, never a clean merge on a revoked ticket. A cancellation of a ticket with a recorded landing, or one git already shows on a default branch, is refused, naming it. A repository with a recorded PR is landed only through that PR (or `GAFFER_PR_LOCAL_FALLBACK=1`), so a ticket is never done with one of its PRs unmerged upstream.
- **For unattended autonomy specifically** (`GAFFER_MODE=autonomous`/`strict`, or the `DISPATCH_ALLOW_AGENT_APPROVE` / `MERGE_ON_AGENT_REVIEW` / `AUTO_MERGE` / `MEMORY_AUTO_APPROVE` / `GAFFER_AUTO_PUSH` flags), the **OS sandbox is the containment boundary** for a determined or prompt-injected agent — in the default supervised mode, the human review gate is that boundary instead. The runner **enforces this in code**: enabling any of those autonomy flags **auto-defaults `STRICT_MODE=1` + `GAFFER_STRICT_REQUIRE=1`**, so the runner fails closed (refuses to launch — `runner/test/autonomy-containment.test.sh` pins every entry point) when no OS sandbox provider is available — unless you *explicitly* set `GAFFER_STRICT_REQUIRE=0` to assert you've supplied containment out-of-band (a VM/container around the whole runner), which is logged loudly. So: run unattended only where an OS sandbox is available — **`SANDBOX_PROVIDER=docker`** for real read+egress isolation on any host with a Docker daemon, or macOS `sandbox-exec` for a write-only boundary — or with explicit out-of-band containment; otherwise keep a human on the gate. (Graduated mode ships only what each repo has *earned* via per-repo/risk policy; the same containment expectation applies at its per-ticket ship gate.)
- Treat the host like one running an autonomous process with shell access: isolated user, no ambient cloud credentials, scoped repo access. The agent's environment is allowlist-scrubbed before each launch, but that is defence in depth — keeping host credentials out of the runner's own environment remains the right posture.
- Prefer running against repos you own, on a machine you control. That is the supported, local-first posture.
