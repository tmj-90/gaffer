# Upgrade a dependency safely

A dependency change imports someone else's decisions into your build. Treat it like a
code change from a stranger: read what changed, run everything that could be affected,
and keep the lockfile honest. Never "bump and hope".

## Steps

1. **Read the ticket's reason.** A security advisory (which CVE, which versions are
   fixed), a feature you need, or hygiene. The reason sets the minimum version and the
   urgency; it does not license unrelated bumps. Call `search_lore` for pinned versions
   and known incompatibilities in this repo.
2. **Read the upstream changelog between the current and target versions.** List
   breaking changes, deprecations, and behaviour changes that touch code you use
   (`grep` for the imports and APIs named in the release notes). A major bump with no
   notes read is a guess.
3. **Bump with the repo's package manager only.** `pnpm up <pkg>@<ver>`, `npm install`,
   `poetry add`, `go get`, `cargo update -p`, `mvn versions:use-latest-releases` — the
   tool that owns the lockfile regenerates it. Never hand-edit a lockfile; never mix
   package managers; never commit a lockfile from a different manager version than
   CI uses.
4. **Keep the scope to the ticket.** One package (and the transitive changes it forces).
   Do not "refresh everything" unless the ticket is a lockfile refresh; a diff of 4,000
   lockfile lines hides the one that matters.
5. **Adapt the code to the breaking changes** you listed, minimally. If the upgrade
   requires a refactor larger than the ticket implies, stop and raise `request_decision`
   with the size and the option of an interim minor bump.
6. **Run the full verification**, not just the unit tests: build, typecheck, lint, tests,
   and any integration or browser suite the repo has — dependency changes break at the
   edges. Check the bundle size or startup time if the repo tracks them.
7. **Audit the result.** Run the ecosystem's audit (`pnpm audit`, `pip-audit`, `cargo
   audit`, `govulncheck`) and confirm the advisory is resolved and no new high-severity
   finding appeared. Check the new version's licence matches the repo's policy when the
   package is new.
8. **Evidence** with the `record-evidence` skill: the version pair, the changelog items
   you handled, the full verification output, and the audit result. Say explicitly if
   a transitive dependency also changed major version.

## Rules

- Read the changelog; a major bump without notes read is not a delivery.
- Lockfiles are generated by the repo's package manager, never edited by hand.
- One package per ticket unless the ticket is a refresh; no drive-by bumps.
- Full verification, including integration/browser suites, not just unit tests.
- New packages need a licence check and a one-line justification in the evidence.
- Never vendor, fork, or patch a dependency to make an upgrade pass without a decision.
- Run on the ticket branch (the `create-branch` skill verifies), never a protected branch.

## Capture lore

This skill is one of the places durable, reusable knowledge naturally surfaces:
**While bumping a package you learn which pins must not move, which packages break each other, and which manager version CI insists on.** That kind of fact is *lore*. Capture it via the **lore-capture
protocol in your brief** (`CLAUDE.factory.md`, step 11 "Memory contribution"):
call the Memory MCP `suggest_lore` once at the close of your work — reusable
conventions, gotchas, decisions, and boundaries only, never per-ticket trivia.
